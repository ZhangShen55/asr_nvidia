# Design

## Context

当前 v2 服务把 CAM++ 和 emotion2vec 模型池放在 `asr-offline-model` 主进程中，VAD worker 通过独立进程运行。每个模型实例都会独立加载一份 `AutoModel`，每个请求还会持有完整音频 Tensor 和在途分段数据。现有状态接口能看到模型池的实例和等待数量，但缺少主机 PSS、Swap、GPU 进程显存、缓存增长和请求阶段的统一时间轴。

本 change 关注“定位问题和指导后续优化”，不以最大化并发为目标。已确认正常的 VAD-only A 项不再执行，Qwen-ASR 继续由独立服务提供并保持运行。

## Goals / Non-Goals

**Goals:**

- 建立可复算的资源时间序列，能把模型常驻内存、音频/段缓冲、请求后未释放、Swap 和 GPU 算力争用区分开。
- 用分阶段测试找到安全的音频并发和段级并发边界，任何异常都在升压前停止。
- 通过请求 ID、模型池统计和系统采样关联 p50/p95 与具体等待环节。
- 产出可以指导后续内存释放、段级队列、准入控制、实例规模和设备分配优化的报告。

**Non-Goals:**

- 本 change 不自动调整生产配置，不修改 VAD 算法，不替换 FireRedVAD。
- 本 change 不实现模型权重共享、TensorRT、NPU 后端或新的推理调度策略。
- 本 change 不停止、重启或修改 Qwen-ASR 服务。
- 本 change 不把监控采样值直接作为业务拒绝条件；生产准入控制另立 change。

## Decisions

### 1. 使用独立诊断采样器和阶段控制器

采用与 ASR 请求逻辑解耦的诊断工具。采样器每秒记录主机、进程、GPU、缓存和端口状态；阶段控制器只负责按清单提交请求、等待完成和执行安全闸门。这样即使业务请求卡住，采样器仍能记录现场。

备选方案是在每个请求内增加大量监控逻辑。该方案会改变请求路径并放大事件循环负担，暂不采用。

### 2. 以 PSS 和增量指标作为主机内存依据

报告同时记录 RSS、PSS、Private 区域和 `VmSwap`，但使用 PSS 评估进程真实内存贡献，使用测试起始值计算 Swap 增量。多个进程 RSS 直接相加会重复计算共享库，不能作为唯一结论。

### 3. 以动态基线计算安全水位

测试启动时记录可用内存、Swap、GPU 空闲显存、进程数和缓存目录状态。黄色/红色阈值使用总内存和 GPU 容量计算，并保留固定安全余量；最终报告同时给出阈值和触发时的绝对值，避免把某台机器的固定数字误用于其他机器。

### 4. 分阶段升压并设置冷却期

测试顺序为模型单独加载、模型同时加载、2/4/8 路音频、段级并发 4/8/16。每阶段完成后冷却 60 秒，只有资源指标回到稳定区间才进入下一阶段。阶段失败不自动重复施压，避免故障被反复放大。

### 5. 统一记录请求级和模型池级时间

每个测试请求带有 run ID 和 request ID。报告把总耗时拆为 VAD、裁剪、Qwen 等待/推理、CAM++ 等待/推理、emotion2vec 等待/推理、聚类和清理，并与系统资源峰值按时间窗口关联。

### 6. 红色告警优先保护服务

出现 Swap 增长、持续 `si/so`、OOM、GPU 显存不足、后端失联或 VAD worker 异常时，控制器停止新请求并优雅停止 SeaCraftASR。停止顺序为停止提交、等待可回收任务、保存现场、确认进程树和缓存；不使用 `kill -9` 作为首选，也不触碰 8806 Qwen 服务。

### 7. 将结论映射到优化方向

报告固定输出四类归因：模型常驻、在途缓冲、请求后增长、GPU 争用。每类归因分别关联实例数量、音频/段并发、对象释放、缓存清理、线程数和设备分配建议，避免只给出“降低并发”的笼统结论。

## Risks / Trade-offs

- [采样本身增加少量 CPU 和 I/O] → 使用 1 秒采样、结构化追加写入，并限制日志字段和文件大小。
- [部分环境没有 `nvidia-smi` 或 PSS 读取权限] → 标记指标不可用并继续采集其他指标，报告中禁止把缺失值当作零。
- [Qwen 响应慢导致阶段长时间占用资源] → 每个阶段设置请求超时和整体看门狗，超时后停止升压并保留 Qwen 健康状态。
- [已有 Swap 使用量影响判断] → 所有判断使用测试开始时的 Swap 基线和增量，而不是绝对已用值。
- [模型池懒加载使单次基线不稳定] → 将冷启动加载和热请求分开记录，每个模型至少完成一次加载后再做并发比较。
- [服务优雅停止失败] → 先停止新请求并等待回收；若进程仍无法退出则标记测试失败、保存现场并停止后续测试，不反复重启施压。

## Migration Plan

1. 先以只读诊断工具采集现有服务，不改变业务配置和请求行为。
2. 完成 B、C、D 阶段测试，生成资源归因和安全并发报告。
3. 根据报告另立 change，实施音频引用释放、段级有界队列、缓存清理加强或内存准入控制。
4. 若新增 `/get_status` 资源字段，先保持向后兼容；字段采集失败返回不可用状态，不影响既有请求。
5. 任何优化出现回归时，只需停用诊断增强或回滚后续 change，不改变 Qwen-ASR 服务。

## Open Questions

- 最终黄色/红色阈值需要在目标机器的模型加载基线完成后固化；本 change 先规定计算方式和停止动作。
- 资源采样原始数据的长期保留周期可在诊断工具稳定后另行确定，不影响本 change 的结构化报告和现场留存。
