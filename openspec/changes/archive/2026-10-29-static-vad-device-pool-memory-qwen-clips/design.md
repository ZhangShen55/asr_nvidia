# Design

## Context

当前服务已经把 FSMN-VAD 放到独立进程 worker 中，也已经把 CAM++ 与 emotion2vec 分成独立模型池。v2 的段处理会先从内存张量裁剪，再把每个段写成临时 WAV，Qwen 客户端重新打开该文件上传；这条路径造成大量小文件 I/O。当前 VAD 池仍保留动态扩容、空闲回收和多个超时配置，导致“完整音频有效并发”不能直接从一个配置数组读出。

本设计遵循变更规格中的两个不变量：一个 VAD worker 同时只处理一个完整音频；一个 VAD 段仍对应一个独立 Qwen request。低音量 RMS/SNR 计算不在本变更中改动。

## Goals / Non-Goals

**Goals:**

- 用 `vad_device` 数组表达固定 VAD worker 数量和每个 worker 的设备，启动时一次性预热。
- 删除动态 VAD 池的运行时扩缩容路径，保证数组长度就是完整音频 VAD 的有效并发上限。
- 让 Qwen 段请求从内存发送 WAV 字节，消除段级临时文件的写入、重新打开和删除。
- 用 `[model_device_pool]` 作为 CAM++/emotion2vec 的唯一设备数组配置，并保留非对称实例数。
- 让状态、日志和测试可以区分 VAD 排队、裁剪累计耗时、裁剪墙钟耗时、Qwen 调用和本地模型池等待。

**Non-Goals:**

- 不合并 VAD 段，不改变 VAD 边界、Qwen 调用粒度、时间轴或 ASR 输入音频内容。
- 不改变低音量过滤的阈值、判定规则或默认开关；其性能优化另立 change。
- 不新增 CAM++/emotion2vec 槽位整数配置，不实现运行时跨模型或跨设备借用实例。
- 不改变 Qwen-ASR 服务端模型、端口、响应协议或 `showSpk`/`showEmotion` 语义。

## Decisions

### 1. 使用设备数组创建固定 VAD worker

服务启动时遍历 `vad_device` 数组，为每个元素创建一个独立 worker 和一份 FSMN-VAD 模型。主进程维护一个 FIFO 完整音频队列；派发时只从空闲 worker 中取一个，worker 完成后立即接收队首任务。worker 不在运行期增加、回收或改变设备。

选择数组而不是 `vad_pool_size + vad_device` 的原因是避免数量和设备列表不一致。选择固定池而不是动态池，是因为上游希望 `len(vad_device)` 直接等于有效完整音频并发，并且每个 worker 的模型显存和 CPU/GPU 资源在启动时可预估。

`audio_concurrency` 仍限制同时进入完整音频处理链路的请求数；它大于 VAD 数组长度时，额外请求在固定 VAD FIFO 中等待。移除可配置的 VAD 排队/调用超时后，客户端取消请求时必须取消对应队列项；worker 崩溃或模型异常仍返回现有 VAD 错误码，不能让队列永久占用槽位。

替代方案是保留动态扩容但把默认上下限设成相同值。该方案仍保留无效配置和动态管理分支，无法清晰表达混合 CPU/GPU worker，因此不采用。

### 2. 以 BytesIO 生成段 WAV 并扩展 Qwen 客户端

`_cut` 继续从已加载的标准化音频张量按 VAD 起止样本切片，并一次性得到：

- 一维单声道 NumPy 数组，供 CAM++/emotion2vec 使用；
- 内存中的 16 kHz 单声道 PCM WAV 字节，供 Qwen 上传。

Qwen 客户端增加内存文件上传入口，multipart 文件字段仍使用 WAV 文件名和 `audio/wav` MIME。保留按 VAD 段独立请求的调度和 `segment_concurrency`/`request_concurrency` 两级信号量。段处理完成后不产生段级临时路径；请求原始音频临时文件仍保留到 VAD 完成和上下文清理结束。

选择内存字节而不是把多个段写入一个临时容器，是因为合并容器会改变 Qwen 输入边界和时间轴。选择复用统一的 WAV 编码函数而不是直接上传裸 PCM，是为了保持当前 Qwen 服务的文件协议和采样格式。

实现时要用解码后的样本对比验证：旧路径和新路径的段长度、采样率、声道数及 PCM 样本一致；只允许 WAV 容器头或等价编码差异。

### 3. 服务自有缓存的严格生命周期

所有需要落盘的请求资源都必须登记到当前请求上下文的资源集合中，创建成功后立即登记，删除操作必须幂等。请求入口和 v2 主流程使用最外层 `try/finally` 清理源音频临时文件；段处理使用每段 `try/finally` 清理兼容路径下的段文件；取消、超时、VAD 异常、Qwen 异常和本地模型异常都只能通过同一组清理函数退出，不能依赖正常返回分支。

服务自有缓存路径必须包含明确的前缀或专属目录，并记录请求标识。启动时可以扫描该前缀下的残留，但必须排除当前进程登记的活动资源，并且不能使用宽泛的 `/tmp/*.wav` 或原始文件名匹配，避免误删其它服务文件。清理失败要记录路径和异常，必要时在请求结束和服务启动的下一次清理中重试；清理失败不能覆盖原始业务错误。

内存上传路径下，Qwen 段不产生文件；因此缓存审计必须同时验证“应该没有段文件”和“兼容回退路径产生的段文件最终为零”。测试采用故障注入覆盖正常完成、任意段失败、任务取消、HTTP 超时、同名并发和进程重启残留。

### 3. 将模型设备配置提升为顶级 `[model_device_pool]`

配置解析层只读取：

```toml
[model_device_pool]
speech_campplus_devices = ["cuda:0", "cuda:0", "cuda:0"]
emotion2vec_devices = ["cuda:0"]
```

模型池的配置实例数直接取数组长度，成功加载数、失败数和可用数分别记录。`features.open_v2_role` 或 `features.open_v2_emotion` 为 false 时，对应数组不触发懒加载；数组为空而请求要求该能力时，保持现有明确的 4015/4016 模型不可用错误。

旧 `[model_device]` 和 `[model_device.local_model_pool]` 不参与容量计算。迁移期间可以检测并记录告警，但不能让旧单设备字段覆盖新数组，否则同一配置会产生不可预测的实例数。

### 4. 拆分裁剪耗时指标

保留当前每个段的累计裁剪耗时，同时增加裁剪阶段墙钟测量：

- `cut_sum_ms`：所有段 `_cut` 耗时之和，用于衡量总 CPU/I/O 工作量；
- `cut_wall_ms`：本次请求第一段裁剪开始到最后一段裁剪结束的墙钟区间，用于衡量请求实际等待时间；
- `segment_wall_ms`：整个段处理阶段墙钟耗时；
- Qwen、CAM++、emotion2vec 的调用累计耗时与池等待耗时继续分别统计。

报告中不把累计值与墙钟值相加，避免并行任务被重复计时。

### 5. 默认配置和迁移顺序

默认配置采用 8 个 VAD 设备元素（CPU 4、`cuda:0` 4）、`segment_concurrency=16`、`request_concurrency=128`、`audio_concurrency=8`，模型池示例采用 CAM++ 3、emotion2vec 1，两个功能开关默认 false。正式配置删除旧字段；测试夹具覆盖旧字段残留时的迁移告警和新数组优先级。

迁移先实现解析和状态兼容，再切换 VAD 固定池；随后切换 Qwen 内存上传；最后更新 README、配置样例和压测报告。任一步出现边界、文本或错误码回归，都可以回滚到旧配置和临时 WAV 路径。

### 6. 控制台日志和段处理进度

日志初始化保持 console handler 与 file handler 分离。只在 console handler 上增加针对 `httpx`/`httpcore` 成功访问 `INFO` 记录的过滤器，不能把全局 logger 级别降到 WARNING，也不能影响 warning/error 或业务耗时日志。文件 handler 继续按现有策略接收完整记录，便于故障审计。

进度条在 `_process()` 确定有效段列表后创建，total 使用短段和低音量过滤之后的段数。每个段通过统一的 `try/finally` 汇总 Qwen、CAM++、emotion2vec 的结果；无论成功、模型错误、Qwen 超时还是取消，都在该段最终退出路径将进度加一，并在失败时增加失败计数。进度状态绑定请求 ID/音频标识，多个音频并发时不能共享计数器。

使用线程安全的进度管理器和 tqdm 的兼容输出接口，普通日志通过 tqdm 兼容写入避免破坏进度行。只有在输出流为 TTY 且 tqdm 可导入时启用动态控制字符；非 TTY、日志重定向或依赖不可用时降级为普通计数日志，不改变段处理结果和错误码。进度对象必须在请求成功、异常、取消和超时后关闭，不能因为异常留下后台刷新线程。

## Risks / Trade-offs

- **[VAD 数组长度小于 `audio_concurrency` 时等待时间增加]** → 启动日志和 `/get_status` 明确显示数组长度、busy、waiting；部署时把上游完整音频并发控制在数组长度以内，或有意接受 FIFO 等待。
- **[混合 CPU/GPU worker 的处理速度不同导致 FIFO 尾延迟]** → 记录每个 worker 的设备和单任务耗时；本次不做动态迁移，后续根据实测决定设备数组比例。
- **[内存 WAV 编码造成额外复制或内存峰值]** → 仅保留 `segment_concurrency` 个在途段，使用 `BytesIO` 生命周期绑定单段任务，并对长音频做峰值内存回归。
- **[删除段级临时文件后 Qwen 客户端或测试打桩仍要求路径]** → 保留兼容的路径入口到迁移完成，并让所有兼容路径资源进入统一登记/`finally` 清理；生产路径和新测试统一使用字节入口。
- **[异常或进程退出留下缓存文件]** → 使用请求资源登记、幂等清理、专属前缀启动扫描和故障注入测试；扫描只处理服务自有且非活动资源。
- **[旧配置未迁移导致服务启动行为变化]** → 启动校验输出字段级迁移提示；默认配置、Docker 配置和配置契约测试同步更新。
- **[进度条与并发日志互相覆盖或在重定向环境产生控制字符]** → 只在 TTY 启用 tqdm，使用线程安全更新和兼容日志输出；非 TTY 使用可解析的普通日志计数。
- **[过滤器误伤 HTTP 错误或业务日志]** → 过滤器只匹配 `httpx`/`httpcore` 的成功 `INFO` 访问记录，并用 warning/error 和文件日志回归测试验证。

## Migration Plan

1. 扩展配置解析和状态结构，支持 `vad_device` 数组与 `[model_device_pool]`，添加新旧配置互斥/告警测试。
2. 将 VAD 池切换为固定 worker，移除动态扩容、回收和相关配置读取，验证 CPU/GPU 混合数组及 worker FIFO。
3. 抽取统一 WAV 内存编码和 Qwen 字节上传接口，保留旧路径兼容入口，完成样本级输入一致性回归。
4. 更新段处理、请求资源登记、幂等清理和耗时指标；验证成功、VAD/裁剪异常、Qwen 失败/超时、模型池为空、取消和客户端断开时资源都能释放。
5. 增加服务启动残留扫描，只清理带服务专属标识且不属于活动请求的缓存；用模拟异常退出和重启测试确认不会误删其它临时文件。
6. 更新 `config.toml`、`config.docker.toml`、README 和状态接口文档，使用 1/4/8 路完整音频比较旧路径与新路径的 P50/P95、CPU、显存、段边界和文本，并输出缓存残留统计。
7. 稳定运行后移除旧路径兼容代码；若出现性能或质量回归，回滚到旧配置结构和临时 WAV 上传实现。

## Open Questions

无。VAD 超出固定 worker 数量时采用 FIFO 等待、取消请求释放队列项的行为已作为本设计决定。
