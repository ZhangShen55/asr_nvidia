# Design

## Context

需求与范围见 `proposal.md`。核心是四个 TensorRT 配置项和现有 `[model_device_pool]` 的实例设备数组；不改变 VAD 后端、分段或过滤规则。

实施基线为 `2026-11-02-split-audio-concurrency-gates` 完成后的代码：总音频准入覆盖 A+B，B 表示请求说话人、情绪或角色识别的音频；能力关闭在准入前拒绝；取消后等待本请求已启动的工作收尾，再归还资源。实现时保留这些语义，不从旧版本覆盖共用模块。

现有独立实验已生成 CAM++ 和 emotion2vec FP32/FP16 engine，文件及报告位于 `model/`。CAM++ 验证 33 个课堂裁剪，emotion2vec 验证 27 个 1～10 秒裁剪，完整情绪分类已成功导出；“能否导出完整情绪输出”已不是待决问题。这些结果尚未覆盖完整课堂、服务运行器、多实例和同卡 Qwen 争用，不能据此认定生产验收完成。

## Goals / Non-Goals

**Goals:**

- 四个参数能够选择实际推理后端，两个模型独立启用和回滚；默认关闭 TensorRT、默认 engine 精度为 `fp16`。
- 按设备数组的每个元素加载实例，保留两个模型池各自的容量、懒加载、FIFO 等待和统计。
- CUDA、CPU、NPU 的上下文与依赖隔离，为后续 NPU 开发保留真实适配入口。
- 正确管理 TensorRT 动态输入、执行上下文、缓冲区、同步与故障状态。

**Non-Goals:**

- 不修改 VAD 模型、worker 设备数组、段边界、环境音过滤、Qwen 协议或文本处理。
- 不改变 A/B 分类、音频准入、Qwen 并发、CAM++ 聚类及情绪业务标签映射；不增加共享模型推理闸门。
- 不进行 INT8、模型训练或 NPU 性能专项优化，不承诺同一 engine 跨 GPU 架构、运行时版本或 NPU 使用。
- 不自动开启生产 TensorRT 开关；NPU 实机质量与性能验收留待具备对应环境后开展。

## Decisions

### 1. 四个配置项与设备数组共用正式配置表

```toml
[model_device_pool]
speech_campplus_devices = ["cuda:0", "cuda:0", "cuda:0"]
emotion2vec_devices = ["cuda:0"]
speech_campplus_use_tensorrt = false
speech_campplus_tensorrt_precision = "fp16"
emotion2vec_use_tensorrt = false
emotion2vec_tensorrt_precision = "fp16"
```

设备数组示例不成为强制默认值。两个开关只接受 TOML 布尔值，精度只接受 `fp16`、`fp32`；缺省值使用上例所列四项。启动时校验配置类型和枚举，不把字符串 `"false"` 解释成 true，也不把其他精度静默修正。修改后重启生效。

不重新引入已废弃的 `[model_device]` 或嵌套模型池。选择共用正式配置表，是为了使设备、实例数与后端选择在同处可查，避免新字段被旧配置迁移逻辑忽略。TensorRT 精度只选择 engine，不修改 PyTorch CUDA、CPU 或 NPU 的原有精度策略。

### 2. 按每个实例的设备解析后端

| 配置设备 | 对应模型 use_tensorrt | effective_backend |
|---|---|---|
| `cuda:N` | true | `tensorrt` |
| `cuda:N` | false | `pytorch_cuda` |
| `npu:N` | 任意 | `torch_npu` |
| `cpu` | 任意 | `pytorch_cpu` |

扩展 CAM++/emotion2vec 的设备校验，不扩展本 change 范围外的 VAD 设备配置。一个模型的开关作用于它的全部 CUDA 实例，NPU/CPU 实例忽略该开关及 engine 精度；不以模型池第一个设备代表整个池。重复设备仍代表多个实例，不因启用 TensorRT 合并实例或绑定两个模型池容量。

`[features].open_v2_role` / `open_v2_emotion` 先决定能力是否开放，请求参数决定是否需要模型，随后才按配置加载运行器。关闭能力时不因 engine 存在或设备数组非空而加载模型，保留既有 4015/4016/4018 的含义。

### 3. 保留模型池，替换实例内部运行器

模型池负责容量、租约和 FIFO 等待；实例句柄关联配置设备、实际后端和运行器。运行器负责设备上下文、精度、输入准备、前向、结果读取和资源释放。上层增强函数使用统一推理接口，不包围所有后端执行 CUDA AMP，不再假设每个实例都是 FunASR AutoModel。

TensorRT、CUDA、NPU 的导入放在各自后端边界内。CUDA 使用正确设备的上下文；NPU 使用独立的 torch_npu 设备与精度 API；CPU 不创建加速器上下文。TensorRT 开关关闭的 CUDA、CPU 和 NPU 路径不要求安装 TensorRT，NPU 路径不调用或初始化 CUDA。

每个 TensorRT 实例拥有独立执行上下文、CUDA stream 和可写缓冲区，并由现有模型池租约互斥使用。不能以全局推理锁把多实例重新串行化，也不能让不同实例同时修改同一 context 或 shape/buffer 状态。

### 4. 推理完成与取消收尾使用同一个资源边界

复用现有 `run_in_thread` / `await_completion` 的收尾语义。TensorRT 异步提交成功只表示工作入队，运行器必须等对应 stream/event 完成，输出读取完成后才返回；发生异常时也要完成必要同步或故障收尾。

请求取消后继续持有模型租约和整音频 A/B 租约，直到已启动的 CPU/设备工作、输出读取及必要清理完成。随后归还模型实例、清理请求文件、释放音频租约，再传播取消。加载中创建但尚未交付给池的资源也需要明确所有者，取消或失败时不能遗失。

使用受控异步提交与延迟完成的桩验证线程函数返回不等于设备完成，另以真实 CUDA 集成验证同步行为；既有阻塞线程测试只能证明线程边界，不能代替 GPU 完成测试。

### 5. 使用已验证的输入边界和完整输出

| 模型 | TensorRT 输入 / profile min、opt、max | 输出 |
|---|---|---|
| CAM++ | FP32 `features=[1,T,80]`；T=50/200/3000 | FP32 `embedding=[1,192]` |
| emotion2vec | FP32 `waveform=[1,N]`；16 kHz，N=16000/48000/160000 | FP32 `logits=[1,9]`、`scores=[1,7]` |

两个 engine 均固定 batch=1；FP16 是内部优化策略，I/O 仍为 FP32。每个 VAD 段独立推理，不跨段拼接，也不对不同段混合填充来改变结果。

CAM++ 调用侧沿用与 FunASR 相同的 80 维、按段去均值 fbank，小于 1 秒的段继续跳过。导出必须保留 52 个 AveragePool 的尾窗口分母修正：`count_include_pad=0`、`ceil_mode=1`。

emotion2vec engine 包括归一化、完整特征网络、移除额外 token、时间均值池化、9 类分类头及去掉两个 unuse 类后的 7 类 Softmax。导出前预热 10 秒 ALiBi 缓存，再按输入长度动态切片。标签顺序及业务映射沿用现有实现；1～10 秒外继续使用既有“平淡”快捷分支，并先执行能力校验。

运行器严格验证输入 shape、dtype、输出维度和有限值。超出 engine profile 的输入显式记录失败，不静默切换 PyTorch，也不擅自截断、补零或拆分音频。需要扩大 profile 时重新导出/构建并验证。

### 6. 模型资产、兼容性与错误分层

资产相对 `[model_paths].spk_model_dir` / `emotion_model_dir` 定位，无需增加 engine 路径配置：

```text
model/<原始模型目录>/tensorrt/<fp32|fp16>/engine.plan
model/<原始模型目录>/tensorrt/<fp32|fp16>/manifest.json
```

保留原始 PyTorch 权重。实验 manifest 和 `model/tensorrt-validation-20261102/evidence/environment.json` 已记录部分来源信息；正式交付需把模型标识、权重/导出代码版本、I/O、profile、精度、构建时间、TensorRT/CUDA、GPU 架构和 SHA256 收敛为可校验 manifest，不能假定现有实验元数据已满足生产加载契约。

现有 engine 针对 RTX 4090 / SM89、TensorRT 10.7.0.post1、CUDA 12.4。加载前针对实例实际设备核验，不能把 CUDA 数字索引当作 GPU 架构或 nvidia-smi 顺序；不同环境不保证直接复用。

无对应能力请求时保持懒加载。只有需要的 CUDA TensorRT 实例要求 engine 资产；开关 false、能力关闭或 NPU/CPU 路径不要求 engine、TensorRT 包和 CUDA engine 校验。

- 配置非法在服务就绪前报字段级错误；开关关闭能力仍在音频准入前拒绝。
- engine 缺失、不兼容或初始化失败使对应实例不可用，记录原因；部分失败沿用健康实例，全部失败按模型返回 4015/4016，普通 A 请求和其他能力仍可用。
- 已有健康实例上的普通段级输入/推理失败沿用 null 回退。上下文已损坏等实例级故障要更新健康状态，不能只打印警告后继续复用；不把双模型加载失败解释成“两项配置关闭”的 4018。
- 任何失败都不自动改变后端。运维关闭对应模型开关并重启，是明确的 PyTorch 回滚方式。

### 7. 状态与性能使用新的并发基线

保留 `audioConcurrency`、`spkEmoConcurrency`、VAD 和既有诊断语义。两个模型池按实例追加 `configured_device`、`effective_backend`、配置 engine 精度、实际计算精度、engine 标识、兼容/失败原因与健康状态，不能把配置值 fp16 当作所有后端的实际精度。

继续区分模型池 busy/waiting、等待和推理耗时与整音频 A/B 等待。TensorRT 使用的非 PyTorch 分配内存不能仅以 `torch.cuda.memory_allocated` 统计后假报为 0；记录可获取的分配/设备指标、统计口径及不可用原因。

当前参考配置为总音频 8、B 上限 4、单音频在途段 16、CAM++ 3 实例和 emotion2vec 1 实例。B=4 不是模型段并发=4；四个 B 音频最多约有 64 个在途段，模型执行仍受各自健康实例数限制。A 请求对同卡 Qwen 的负载也须计入。

对比实验固定 A/B 请求比例、总/B 上限、段并发、Qwen 全局并发、模型数组、VAD 和同卡 Qwen 负载，仅改变被比较模型后端或精度。默认 B=4 时八路增强提交须记录已准入、拒绝/等待及端到端结果；测试八个活动 B 时须显式把 B 上限改为 8，并在 PyTorch/TensorRT 两组一致设置，不能把限流收益算作 engine 收益。

```toml

speech_campplus_devices = ["cuda:0", "cuda:0", "cuda:0"]
emotion2vec_devices = ["cuda:0"]

[features]
open_v2_role = true
open_v2_emotion = true
```

统计与交付口径如下：

- 主指标为逐音频客户端端到端耗时，使用单调时钟，从该请求发起上传/HTTP 调用到完整读取最终响应，包含上传、准入/排队、VAD、分段链路、聚类/汇总与响应读取。服务端处理耗时、单段推理耗时和模型池等待另列，不能替代主指标。
- 每组至少一轮完整八路测量。每轮单独用 8 个成功完整请求的耗时计算 P50/P95，报告样本数 `N=8`、单位秒和线性插值方法：排序为 `x[0..7]`，`h=(N-1)*p`，按相邻次序统计量线性插值。P95 是该小样本批次的描述值，不宣称稳定的生产尾延迟；如重复测量，保留各轮结果，合并统计须单列轮数和总 N，不能混合不同后端或精度。
- 逐音频列出路径、原始时长、请求标识、开始/结束时间、耗时、RTF、VAD 段数、成功/失败状态及错误；同步列出实际 CAM++/emotion2vec 调用、跳过/失败和 null 情况，防止未调用增强模型或推理失败回退被误算为加速。
- 同时报告整批从最早请求开始到最后请求结束的墙钟耗时、成功数/8、总音频时长/批次耗时的吞吐、显存/GPU 及准入/模型池观测。RTF 为各请求耗时/其原始音频时长；P50/P95 不是整批耗时，也不是音频自身时长的分位数。
- 若存在拒绝、超时、异常或未完成，完整列出，标记该轮八路验收不完整；可另列成功子集及其 N，但不能丢弃失败后仍标称完成了八路 P50/P95。保存原始逐请求测量、返回结果与配置，使分位数和质量对比可复算。

## Risks / Trade-offs

- [短段中 FP16 不一定比 FP32 更快] → 保留两种 engine，用真实段长分布比较；默认配置精度仍为 fp16。
- [FP16 改变分类或聚类边界] → 先复核 FP32，再比较 FP16 和当前 PyTorch；增加完整课堂、低置信度和类别接近样本，业务回归未通过不生产启用。
- [模型层加速无法直接换算接口加速] → 分别报告预处理、传输、模型推理、排队、Qwen 和端到端指标。
- [取消时设备工作尚未结束] → 以设备完成作为租约释放前提，补充重复取消和异步提交测试。
- [当前无 NPU 实机] → 先验证设备选择、依赖隔离及可替换运行器，报告明确未实机验证；后续独立环境验收，不宣称复制 NVIDIA engine 即可迁移。

## Migration Plan

1. 确认并发 change 已完成，并冻结实施时的代码、配置和实验资产版本。
2. 实现四个配置项、运行器及状态扩展，默认均不启用 TensorRT，先完成现有 PyTorch CUDA/CPU 回归。
3. 整理可复现导出与正式 manifest，在目标设备核验现有 engine；CAM++ 先 FP32 再 FP16，随后对 emotion2vec 重复完整输出与业务验证。
4. 完成默认 A/B 配置下的租约、取消、错误和同卡性能测试，再按模型单独灰度；部署和开关启用另按用户授权执行。
5. 回滚时关闭故障模型的 TensorRT 开关并重启，保留另一模型的选择，核对状态实际后端及同批输入结果。
