# Design

## Context

动机与初始范围见proposal.md。多owner已正式实现；N6纯A6墙钟186.32秒，但增强驻留A6真实OOM，N5补测共驻A5墙钟206.12秒且未复现OOM。2026-11-24用户采纳最终Qwen4／CAM4／emo1，剩余验收改为该配置B4及同a1～a4增强驻留A4。这是替代最终范围，不能冒称原N6共驻通过，全部原始结果保留。主规格与未归档change处理见spec-sync-order.md。

## Goals / Non-Goals

**Goals:** 用一个HTTP协调进程管理可重复使用的Qwen owner池，配置、准入、取消、状态和关闭成为一致的正式能力；保留N6/N5历史，用最终N4/CAM4/emo1正式服务验证B4与增强驻留A4功能、资源和实际效率。

**Non-Goals:** 不迁移到OM/vLLM、不改权重/BF16/依赖，不重写VAD、复读恢复、prefill/KV或ITN算法，不按Qwen数复制HTTP/VAD/增强服务，不承诺八音频或B4也能200秒，不实施Docker上线。当前修订不新增N6/N5压力，不同步main或归档；最终验收完成后另行处理。

## Decisions

### 1. 配置与容量只有一个权威来源

正式默认采用以下配置。N表示Qwen进程数，S表示每请求活跃段上限；所有参数修改后重启生效。

```toml
instance_count = 1  # HTTP部署数，不是Qwen实例数
[qwen_asr]
generation_mode = "continuous"
execution_mode = "process"
preload_on_startup = true
local_instance_count = 4
local_device = "npu:7"
segment_concurrency = 16
audio_spk_emo_concurrency = 4
max_batch_audio_frames = 14400
max_batch_tokens = 10000
```

最终model_device_pool设备数组为CAM++四个npu:7元素、emotion2vec一个npu:7元素；容器均按实际可见映射改用逻辑npu:0。数组显式独立配置，不从Qwen数派生。

配置实际所属表按现有loader校准，不以示例机械搬动HTTP字段。continuous中audio_concurrency=N、request_concurrency=N×S；根/Docker模板删除这两个重复赋值，并不显式固定随S派生的物理步或prefill上限，兼容读取显式相等值并给迁移提示，冲突值或非法类型/范围必须启动前失败，不静默忽略。legacy只在明确选择时保留其原有独立参数行为。N不写死4，合法整数1～8仍保留；配置npu:x支持部署选择，本轮只验证宿主7。仅映射物理7的容器使用逻辑npu:0，并解释映射。

每owner只有一个设备执行循环，逻辑活跃上限S。物理步max_inference_batch_size默认随S取值；显式值必须不超过S。prefill可选配置的缺省上限派生为min(16,S)，显式值不得超过该值，这些都不构成整批generate屏障。帧14400/token10000是已测S16每owner预算，N变化不缩小或放大该值；更改S或max_new_tokens时校验估算可接纳单段，按需显式调整并报告有效预算，不宣称HBM保证。状态区分每owner预算和全局理论和，禁止把原global60000/86400直接作为每owner默认。全服务PCM保留已测256段/256MiB预算，不按N复制；按现有反压方式公平供给。

B配置上限独立默认4，有效上限min(4,健康Qwen容量)；最终N4为总4/B4/global64。总满时新A/B均4013优先，当前配置不能单独触发仅B满4017；4017仍适用于显式总容量大于B上限的配置。原N6下4B+2A和第五B4017实测保留为历史，不伪装本轮N4可达状态。Qwen每owner线程预算1，VAD8、父进程OMP/MKL4沿用实验有效配置，启动状态记录实际值，避免N倍线程过订阅。替代方案“继续手填audio/global”和“每副本复制global预算”容易配置漂移及内存放大，故不用。

### 2. 按请求动态租用，结束后可供任意新请求复用

准入与owner授予为同一原子流程：等待中的请求不占一个假owner；授予后以request_id关联一个健康owner，整条音频生命周期保持，直到模型在途工作、增强分支及临时资源完成安全收尾再释放一次。文件名、SHA、来源序号均不能参与固定路由。同一文件重复并发、随机新文件名、乱序和下一请求复用均必须可用。

每条音频最多S段进入Qwen，某段EOS/异常终态后独立归还credit，后续段在安全设备步间进入；不等待其他15段或其他音频。active state按owner隔离，不跨owner迁移KV；共享NPU并不承诺kernel物理同时执行。慢增强不持有已完成的Qwen段credit，但可能通过有界PCM产生正常反压。相比共享跨owner段队列，请求租约与已测实验一致，状态和取消边界更清楚；代价是某音频先结束后不能迁走其他音频已执行的段，须在真实混合长度请求中量化。

### 3. 实例生命周期、故障与正常关闭

主进程只协调，N份Qwen权重由owned spawn进程加载；VAD固定池、CAM池、emo池各自独立。默认顺序预加载N个owner，全部真实加载成功且健康后服务才ready；任一失败完整回滚本次部分启动，不能留下后台模型或假满容量。显式preload=false仍允许按需加载，查询状态不触发加载；CAM/emo保留既有按需行为和共享加载锁。每份暖身必须有真实forward/prefill证据，不能把READY或N次HTTP请求当覆盖N实例。

状态至少区分configured/healthy/leased/available owner、各实例PID与出生时间、设备、加载/错误、活跃段及队列与有效容量；保留接口已有字段。运行中坏owner隔离，已接收工作不得静默迁移或重复推理；其请求按现有4011/4012语义失败或段异常规则收尾，其余健康owner继续。全部失效返回既有不可用错误；不引入未经验证的自动重启。

取消和超时仅表示业务停止等待，设备未完成前不能复用owner、PCM或credit。关闭先停止接单，再HTTP drain30秒，所有Qwen/增强/VAD终态确认，模型关闭grace120秒、外层owned回收210秒；重复取消/关闭幂等，按PID+birth核对全部后代。正常close失败必须报告失败，最终强制兜底不记正常通过。保持共享PID1601397及非本轮服务不受影响。

### 4. B类三路并发与独立增强池

沿用VAD→过滤<0.3秒→取得段credit/PCM→裁剪→创建Qwen、CAM++、emo三个异步任务→汇合的顺序；分支有独立池等待，不能串成Qwen完成才调用增强。Qwen完成先返其credit，PCM等三路均终态才释放；请求owner到整条音频安全收尾才归还。CAM对有效段推理；emo仅1～10秒（含边界）真实推理，其他按现有规则平淡，必须区分skip和NN成功。各段汇合后执行现有整音频声纹聚类、ITN和输出拼装；不在本change改变执行器，只分列耗时。

CAM/emo设备数组与池规模独立，不随N、S或B4自动复制。原N6从CAM/emo各1起的标定因共驻OOM停止，N5各1补测亦保留。用户最终选择Qwen4/CAM4/emo1，剩余只在四份Qwen驻留下真实验证该组合B4及增强驻留A4，记录吞吐/HBM/正确性并冻结loader、根/Docker及说明；不再盲扫2/4/8组合，不能用原1/1成绩宣称最终4/1已通过。加载共享锁耗时单列，冷态与暖态不混算。

准入探针独立于计时轮：最终N4下4A、4B或总计4个混合请求均使总满，新A/B均4013优先，不能要求此配置单独触发4017。原N6的4B+2A、总未满第五B4017实测保持历史；通用错误优先级、能力关闭/无健康实例和排队4010不变。HTTP200不等于增强成功，须核对真实NN覆盖、skip、降级、speaker聚类及emotion字段。

### 5. 真实服务验证与性能边界

完整步骤见test-plan.md。先完成源码/保护目标回归并冻结源码，已完成的N6 A6/A4/B4及失败共驻A6、N5补测保留。剩余由root独占NPU7，在最终N4/CAM4/emo1配置下完成固定a1～a4的B4，再保留全部模型驻留执行同源纯A4；必要暖身/基线、N4准入和收尾证据单列。均为正式源码、完整WAV、真实v3 HTTP共同起跑，禁VAD结果缓存、实验环境开关及SHA路由。隔离部署副本仅允许与正式源码逐文件相同并记录导入来源，调参只改配置。

纯A目标墙钟约200秒（N6历史A6与最终增强驻留A4各自单列），不从单轮实验保证；>200且<336如实记未达目标并分析，禁止缩短音频、删段、降低生成上限或扩大文本丢弃换成绩。达到336秒、推理OOM、owned故障或明确无进度立即停止、采证与收尾，不自动扫下一档。用户已取消free-HBM<8GiB提前停止，本验收不得恢复或换成另一free阈值；继续采样实际HBM/host/swap，真实故障仍停止。B4没有擅自继承200秒承诺，也遵守336秒停止条件。完整样本与删失样本分开，不能将完成子集分位数标作全批。

### 6. 并行实施与交付边界

apply时可并行：A负责配置/loader/模板/迁移测试；B负责owner运行时/租约/故障/状态，独占client/process相关文件；C负责B分支、独立增强池与字段覆盖；root负责API接线冲突、测试控制器、完整review及NPU。共享文件提前指定唯一作者，其他人只出补丁建议。CPU任务使用各自guard和私有cache/TMPDIR；全部CPU进程结束才进入NPU验收。不能多个agent抢NPU、端口或同一日志。

## Risks / Trade-offs

- N6增强共驻已真实OOM、N5未复现但共驻A5超200目标 → 原失败保留；用户显式改选最终N4/CAM4/emo1，仍须真实共驻验收。不得自动降档重试或恢复8GiB线，N4不冒充N6通过。
- 请求级绑定遇到长尾 → 记录owner活跃区间与租约等待；跨owner迁移是后续独立议题。
- 同步ITN/聚类阻塞事件循环、提交线程与裁剪竞争仍存在 → 此次保留测量，不能声称已消除；后续凭真实数据另立优化change。
- 16段警告的历史质量风险 → 保持已批准策略并逐段对照；无人工真值不宣称98%召回或无质量退化。
- 旧未归档delta会覆盖新默认 → spec-sync-order.md覆盖表与临时合并严格校验；本轮不归档、不同步main。

## Migration Plan

1. 保存当前正式默认与源码版本；按任务实现可选多owner路径与完整回归，不改权重/依赖。
2. 同步loader、根/Docker模板、README和部署说明：最终默认continuous/process/N4/S16、总4/global64、per-owner预算、B4及CAM4/emo1；N合法1～8仍保留。明确旧冲突配置迁移和重启要求。
3. 冻结正式源码与最终配置、构建保护版本、核对每实例真实导入/暖身；执行test-plan验收并保留逐文件指标和输出。
4. 未达性能/功能/正常关闭条件就保留失败报告与未勾任务，不宣称完成。回退用原配置及已记录源码版本；不得复用在途owner或重写历史。
5. 5.3最终共驻标定/配置冻结与5.6增强驻留A4当前未勾。验收完成后root提交证据，再另行按覆盖表同步可接受规格并归档；本轮不执行同步/归档，旧change与N6/N5保持原事实，不替代未通过旧矩阵。
