# Design

## Context

当前 `core/models.py` 已为 CAM++ 与 emotion2vec 建立两个独立 ModelPool，每个实例有独立锁；但 `api/routes/asr_qwen_common.py` 在两个模型调用前共用一个 `local_gpu_concurrency` 信号量。该信号量把两个模型的并发容量合并，且其等待时间未在模型池状态中体现。设备数组已经表达了副本数量和落卡设备，因此不再增加模型槽位配置。

## Goals / Non-Goals

**Goals:**

- 让 CAM++ 和 emotion2vec 以各自设备数组的成功加载实例数独立控制并发。
- 让两个模型池分别记录 busy、waiting、实例租约等待时间和推理耗时。
- 保持 Qwen 请求并发、单音频分段并发、音频请求并发和 VAD worker 池互相独立。
- 支持任意设备数组长度和比例，完成 CUDA 0 上 6 CAM++ + 2 emotion2vec、8 路完整音频验证。

**Non-Goals:**

- 不新增 `cam_slots`、`emo_slots`、固定比例或新的模型并发配置。
- 不实现 CAM++ 与 emotion2vec 实例互借，不实现运行时自动迁移 GPU。
- 不改变 v2 响应结构、CAM++ 音频级聚类边界、emotion2vec 标签映射或 Qwen 服务协议。
- 不把同一张 GPU 上的多模型争用隐藏为“自动优化”；显存和 GPU 竞争由状态与测试报告揭示。

## Decisions

### 1. 以设备数组作为唯一模型容量来源

`speech_campplus_devices` 的有效元素数量决定 CAM++ ModelPool 的实例数，`emotion2vec_devices` 的有效元素数量决定 emotion2vec ModelPool 的实例数。空数组仍表示禁用，加载失败实例不占容量。这样 3:1、6:2 或其它组合都由配置直接表达，代码不需要知道比例。

替代方案是增加两个整数槽位配置，或继续保留一个全局 `local_gpu_concurrency`；前者会产生重复配置和不一致风险，后者正是当前两个模型互相排队的原因，因此不采用。

### 2. 用独立模型池租约替代共享模型闸门

删除 CAM++/emotion2vec 共用的 `_local_gpu_semaphore`。每个模型调用直接租用对应 ModelPool 的一个实例，实例锁保证同一模型对象不被并发调用，池内其它实例可以并行运行。`local_gpu_concurrency` 不再作为模型池容量来源，迁移时从正式配置和运行路径移除；旧配置若仍包含该字段不应改变数组定义的容量。

该方案允许同一张 GPU 上的总本地推理数等于两个设备数组成功实例数之和，代价是可能增加 GPU 争用；这由显存、GPU 利用率和尾延迟测试决定，而不是用一个隐式全局槽位重新绑定两种模型。

### 3. 为模型池建立公平等待

ModelPool 租约调度维护等待队列和可用实例游标，按先入先服务选择实例；请求上下文携带音频请求标识时，在同一模型池内按请求轮转，避免单个长音频一次性创建大量分段任务后长期占满队列。取消、异常和模型加载失败都必须释放租约并唤醒后继等待者。

### 4. 拆分耗时指标

请求级统计拆分为：CAM++ 等待时间、CAM++ 推理时间、emotion2vec 等待时间、emotion2vec 推理时间、Qwen 等待/调用时间、VAD、裁剪、聚类和 ITN。`/get_status` 暴露当前 busy/waiting，压测报告使用请求级累计值和墙钟值分别解释排队与计算，避免把 ModelPool 等待误报为 Qwen 耗时。

### 5. 保留 Qwen 和 VAD 的独立并发边界

`segment_concurrency` 继续限制单个音频发往 Qwen 的 VAD 段数，`request_concurrency` 继续限制所有音频合计的 Qwen 请求数，音频队列和 VAD worker 数量保持原有配置。CAM++/emotion2vec 等待不能改变这些上限；每个 VAD 段仍同时创建 Qwen、CAM++ 和 emotion2vec 任务。

### 6. 采用可重复的非对称压测

测试服务使用端口 8084，Qwen-ASR 依赖固定为已运行的 8806，测试完成只停止 8084。测试配置临时设置两个模型均为 `cuda:0`，CAM++ 设备数组 6 个元素、emotion2vec 设备数组 2 个元素，执行 8 路同一完整音频并记录冷启动和预热后的数据；6:2 只作为验证组合，不写入默认配置。报告同时记录模型池等待、GPU 0 显存/利用率、P50/P95、吞吐、错误和结果一致性。

## Risks / Trade-offs

- **[同卡总实例过多导致争用或 OOM]** → 启动时隔离失败实例，状态暴露成功/失败数量；压测逐步增加数组长度并记录显存峰值，不把 6:2 固化为生产值。
- **[独立池造成某一模型队列过长]** → 暴露每池 waiting 和等待耗时，使用请求级公平调度；通过数组比例调整容量。
- **[移除全局闸门后 GPU 推理同时过多]** → 不引入新的隐式模型槽位；通过设备数组显式控制总实例数，必要时在后续变更中设计设备级资源治理。
- **[旧配置仍含 local_gpu_concurrency]** → 在迁移文档中标记其不再控制模型池，并在配置测试中确认设备数组才是容量来源。

## Migration Plan

1. 先实现独立租约、等待统计和公平调度，保留默认单元素设备数组，验证 `showSpk=false`/`showEmotion=false` 不回归。
2. 删除正式配置中的 `local_gpu_concurrency`，让两个设备数组成为唯一模型实例配置；空数组和部分加载失败继续按既有契约处理。
3. 使用临时配置在 CUDA 0 上执行 CAM++ 6、emotion2vec 2 的 8 路完整音频冷启动与预热压测，保存原始 JSON、服务日志和中文报告。
4. 若 6:2 出现 OOM、尾延迟或质量回归，回滚到设备数组单元素或其它实测组合；不需要改变 `instance_count`、Qwen 端口或 API 协议。

## Open Questions

无。实例比例和最终生产数组由压测结果决定，不作为代码默认值或固定规则。
