## MODIFIED Requirements

### Requirement: 启动时固定预热 VAD 实例
服务 MUST 仅按 `[vad].vad_device` 数组在启动阶段以 spawn 创建固定 VAD worker 池，数组每个元素对应一个独立 worker，按 FIFO 分派任务；旧 `[qwen_asr].vad_device` MUST NOT 作为配置回退。启动完成前 MUST 记录每个 worker 的设备及预热成功或失败状态，无可用 worker 时 MUST 拒绝就绪。运行期 MUST NOT 因等待队列自动扩缩容；NPU 预热失败 MUST NOT 静默改走 CPU。

#### Scenario: 默认混合设备配置
- **WHEN** 使用本轮吞吐验证配置`[vad].vad_device`的八个cpu元素启动服务
- **THEN** 固定池含八个独立CPU worker并逐一报告预热与健康状态，八CPU验证必须确认健康数为8；仍支持通用CPU/NPU设备数组，NPU实例的容器编号按实际可见映射核对，历史Scenario标题不代表默认仍混合落卡

#### Scenario: 启动时设备不可用
- **WHEN** VAD 数组中的某目标设备不可用或对应 worker 预热失败
- **THEN** 服务记录该 worker 的设备和失败原因，不将其计入健康容量；无成功 worker 时拒绝完成服务启动，不以动态扩容或 CPU 回退掩盖失败

#### Scenario: 部分worker失败的性能报告
- **WHEN** 配置八CPU worker但只有部分健康
- **THEN** 保留实际可用容量与失败原因，不将该轮算作八健康VAD实例通过；不能动态补worker或仅凭配置长度声称八并发能力

### Requirement: 默认配置体现有效并发来源
默认配置 MUST 使用VAD设备数组、CAM++/emo各自设备数组表达配置实例数，用音频总上限及B子上限表达准入，用单音频/全局Qwen窗口表达逻辑段在途。实例数、每实例预取等待深度与实际计算批大小 MUST 分别配置及说明，队列容量不增加模型实际执行容量。MUST 不保留已删除的动态VAD池字段或旧设备结构；新增可调项须同步加载校验、宿主/容器模板、README及配置契约测试。

#### Scenario: 检查默认配置
- **WHEN** 运维读取 `config.toml` 或 `docker/config.toml`
- **THEN** 能直接区分VAD和模型池实例数、总/B准入、Qwen逻辑段窗口、预取等待深度与实际批大小；没有额外共享模型执行槽位，新增队列配置不改变健康实例容量

#### Scenario: 功能关闭时模型池不生效
- **WHEN** `open_v2_role=false` 或 `open_v2_emotion=false`
- **THEN** 对应模型设备数组不会触发模型加载或推理，但配置仍可保留用于重启后开启功能

### Requirement: 八路完整音频报告必须提供可复算的 P50 和 P95
完整音频验收 MUST 使用同一份按完整源文件SHA256去重的八条清单，在1/2/4/8并发各处理全部八文件，完成同源A/B配对并补默认B4的八路混合。B8容量测试单独配置子上限8。MUST 保持模型、有效精度、生成参数和本轮过滤配置一致，分离冷/暖态，报告实际活动峰值和真实批分布。旧g1/g2、三CAM/一emo属历史结果，不代替本轮。各轮MUST 保留逐请求客户端起止、elapsed、批次起止、N、线性插值P50/P95及共享干扰；触发420秒诊断、拒绝或未完成如实记录，不能丢弃失败形成偏置通过结论。

#### Scenario: 八个成功完整请求的分位数
- **WHEN** 某档位的一轮八个完整请求全部成功完成
- **THEN** 从逐请求单调时钟的客户端端到端耗时计算秒单位 P50/P95，起点为该请求上传/HTTP调用，终点为完整读取响应；报告 N=8、线性插值方法与小样本限制，不以单段、原音频时长或整批墙钟代替。重复轮次分别报告，合并统计另列轮数和 N

#### Scenario: 测量清单与复算证据
- **WHEN** 交付本轮1/2/4/8任一并发档位、A/B配对或八路混合测量结果
- **THEN** 保留每个样本的稳定ID、原路径编码、完整时长/大小/SHA256与验证方式、请求能力、配置/环境、原始客户端端到端 `elapsed_s`、计时边界和可获得的时间戳、RTF、VAD段数、状态及适用的增强调用/跳过/失败/null情况；记录实际总/B活动峰值、整批墙钟、成功数/8、音频吞吐、HBM/host资源与共享卡干扰。逐请求原始 `elapsed_s` 与计算方法可独立复算；本轮必须同时保存每请求和整批单调钟起止、UTC关联时间及实测elapsed；客户端本地待提交等待不混入单请求服务时延但计入整批耗时，服务准入等待计入端到端。历史缺失字段明确列缺失，不追造时间戳；不能用重复短片暖标定替代完整清单

#### Scenario: 八路批次存在失败或拒绝
- **WHEN** 八个请求中任一被拒绝、超时、异常或未完成
- **THEN** 完整列出错误并标记该轮不完整，不丢弃失败或补测后仍称原轮八个完整成功请求；成功子集另列时明确样本数。每批次统一关闭 owned 服务与worker，等待在途工作结束并检查逐worker退出、无孤儿/剩余监听；共享既有服务保留，关闭超时或强制处置不得被改写为验收通过

#### Scenario: 一二四八并发工作量一致
- **WHEN** 同一八文件清单分别在1、2、4、8客户端在途限制下执行
- **THEN** 每档仍处理完整八文件、完成即补下一条，分别报告整批墙钟、完整源音频秒/墙钟秒及单请求分位数；不以减少文件数制造高并发收益，单请求RTF与整批吞吐不混用

#### Scenario: 同源A与B配对
- **WHEN** 同一完整源文件分别以A和B双能力请求执行
- **THEN** 使用相同有效PCM/VAD清单与调度设置，showRoleIdentify未传或为false，逐文件比较排队与执行增量；B4与B8结果分列，实际拒绝/等待不冒称已准入并发

#### Scenario: 最终候选重复轮次
- **WHEN** 某候选通过分层试验进入最终完整音频验收
- **THEN** 对计划的每档最终A/B配置至少执行两轮暖态、每轮各八文件，逐轮列N=8及分位数，合并另列N和轮数；中止轮次不混入成功轮，冷启动单列且不冒充暖态

## ADDED Requirements

### Requirement: 七分钟诊断闸门及时中止盲目压测
性能测试 MUST 以420秒为诊断阈值，检测已完成请求的P50/P95以及所有未完成请求的端到端墙钟。任一超过阈值 MUST 在下一监测周期内停止追加负载并捕获全流程卡点，随后有界诊断和安全收尾；阶段长时间无进展也须提前告警。监测周期、无进展阈值、诊断窗口及收尾期限 MUST 有限且可配置。该规则 MUST NOT 改变业务HTTP超时、错误码或单Qwen调用超时。

#### Scenario: 无完成样本但已有请求超过七分钟
- **WHEN** 某完整音频仍在处理且从客户端开始调用的墙钟超过420秒
- **THEN** watchdog无需等待最终P50/P95，至迟下一个监测周期触发诊断；记录请求年龄、阶段、队列及进度，不能因暂无成功样本跳过检查

#### Scenario: 完成分位数超过阈值
- **WHEN** 当前完成样本P50或P95超过420秒
- **THEN** 立即停止追加测试请求并记录触发时间、样本数和计算口径，对所有流程检查卡点，不继续原样盲跑整轮

#### Scenario: 诊断轮次结束
- **WHEN** 本轮触发七分钟或无进展诊断并完成有界取证
- **THEN** 标记diagnostic_aborted，保留成功/失败/未完成与原因，按测试资源所有权安全关闭服务、worker及端口；强制回收或收尾超时保留失败结论，定位与小规模验证后才恢复完整测试

#### Scenario: 420秒与已有推理超时并存
- **WHEN** 单段Qwen达到已有请求超时而整音频尚不足420秒，或整音频有进展但已超过420秒
- **THEN** 前者按原推理超时处理，后者仍触发全流程诊断，两个机制不互相覆盖，不新增业务错误码

### Requirement: 全流程诊断能够区分队列计算与同步等待
内部遥测 MUST 分开记录准入、解码、VAD等待/检测/过滤、纯切片、各模型队列等待/执行/收尾、批等待、特征处理/传输/生成/读取同步及汇合后处理，并关联请求、段和物理批ID。MUST 记录队列长度、最老任务、实际批分布、健康/busy实例、CPU及本项目/共享NPU资源。不可测细项明确未知；并行累计和批成员包络不能当作设备独占忙时。

#### Scenario: 超七分钟时定位卡点
- **WHEN** watchdog触发全流程诊断
- **THEN** 快照可判断待处理任务卡在准入、VAD、Qwen、CAM++、emo、汇合或后处理，包含对应队列、最老等待、阶段完成数及资源采样；不能只输出总耗时

#### Scenario: 切片之前存在名额等待
- **WHEN** 某段先等待调度名额再执行PCM切片
- **THEN** 新纯切片指标只测切片操作，名额等待另计；旧含等待指标保留原口径并明确标注，不将旧cut_sum_ms称纯切片CPU耗时

#### Scenario: 同一物理批包含多个请求
- **WHEN** 一次物理批完成多个独立段
- **THEN** 批执行包络按批ID保存，各成员保持归属；报告不把同一包络按成员重复相加当设备时间，设备级同步与实际核执行未能区分时明确限制

### Requirement: 容量试验与性能最优结论分开报告
系统 MUST 分别报告单份权重加载增量、allocator allocated/reserved、完整服务峰值和设备聚合HBM，allocated与reserved不能相加。实际批1/8/16/32/64/128容量与性能 MUST 逐档列证据，未执行或失败如实记录；最快合格批可小于128，但必须明确128目标的验证结论。多副本回退仅在单份出现容量/效率问题后执行，不能仅用权重乘法证明八份可运行。

#### Scenario: 64批快于128批
- **WHEN** 两档均实际执行且64批在质量和稳定性合格下吞吐更好
- **THEN** 报告分别列容量、吞吐、P95与峰值HBM，按最快合格档选择交付值并保留128配置/试验结论，不把较大批强称更快

#### Scenario: 128容量验证失败
- **WHEN** 单份在真实目标长度分布下无法执行128成员批次
- **THEN** 保留失败原因及输入预算，诊断后评估适用的2/4/8份回退；全局128逻辑段、单批128和多份合计128分别报告，不相互替代

#### Scenario: 完整B配置的128容量
- **WHEN** 纯Qwen环境实际128批通过且需要验证完整B配置容量
- **THEN** 在八CAM++、八emo均已加载且实际工作的环境单独验证128，即使128不是最快档；未测或失败时明确该资源条件下容量未通过，不能以纯Qwen成功替代
