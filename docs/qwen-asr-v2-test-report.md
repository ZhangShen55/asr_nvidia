# Qwen3-ASR v2 接口测试报告

本报告记录 `2026-10-22-adapt-qwen-asr-v2-interface` 变更的效果、性能与边界验证结果，作为生产并发参数（`audio_concurrency` / `segment_concurrency` / `request_concurrency`）的取值依据。

## 1. 测试环境

| 项目 | 配置 |
|------|------|
| 服务端 | 本仓库 `refactor/adapt-qwen-asr` 分支，Conda 环境 `asr`（Python 3.11），`uvicorn main:app` |
| Qwen 服务 | 独立容器 `qwen3-asr-0.6b-8806`（`qwenllm/qwen3-asr:latest`，vLLM 0.14.0，`Qwen3-ASR-0.6B`，`max_model_len=4096`、`max-num-seqs=32`），宿主 `192.168.29.12:8806` |
| GPU | 3 × RTX 4090。Qwen 容器在 **GPU 0**；本服务的 v1.1.8 链路在 GPU 1；**压测时 v2 链路的 VAD / CAM++ / emotion2vec 单独放 GPU 2**，避免污染 Qwen 侧算力曲线 |
| 压测音频 | `test/audio_file/` 三段真实课堂录音（教师1 47min、课堂实录 55min、储能学术英语实践 52min），另切出每段前 10 分钟窗口用于重复对比 |
| 压测主体 | `zh600.wav`（10 分钟中文，VAD 切出 118 段） |

> 说明：生产默认配置为三个 v2 模型同落 GPU 0（`[model_device]`），但压测统一改到 GPU 2，以便把「Qwen 容器的算力曲线」和「本服务 role/emotion 的算力曲线」分开观测。两者互不影响结论。

## 2. 效果测试（v1.1.8 与 v2 对比）

### 2.1 转写文本

| 音频 | v1.1.8 段数 | v2 段数 | 字符一致率 | v2 独有长插入（幻觉嫌疑） |
|------|------------|---------|-----------|--------------------------|
| zh600（10 分钟中文） | 216 | 118 | 0.9095 | 0 |

- v2 的段数少于 v1.1.8 是**预期行为**：v1.1.8 走 Paraformer 的句子级切分，v2 走本地 FSMN-VAD 的语音段切分，粒度更粗但语义完整。
- 逐段核对未发现漏字成段、连续重复成段或 v2 独有的长插入；`1111`、`这个这个这个这个` 这类片段在 **v1.1.8 输出中同样存在**，属于音频本身而非幻觉。

### 2.2 role / emotion（10 分钟窗口，按时间重叠对齐后逐段比对）

| 音频 | v1.1.8 段 / v2 段 | role 聚类一致率 | role 语义一致率 | emotion 标签一致率 |
|------|-----------------|----------------|----------------|-------------------|
| 课堂实录 | 108 / 78 | 0.8312 | **1.0000** | 0.8182 |
| 教师1 | 189 / 105 | **1.0000** | **1.0000** | 0.8077 |
| 储能学术英语实践 | 147 / 111 | **1.0000** | **1.0000** | 0.6182 |
| zh600 | 216 / 118 | 0.9487 | **1.0000** | 0.7949 |

- **role 语义一致率（teacher / student 分类层面）四段全部为 100%**，达成 ≥ 90% 目标。
- **role 聚类编号层面**（把 v2 的 `spk_N` 与 v1.1.8 的 `spk_N` 按时间重叠做最佳匹配）：单说话人音频为 100%，三说话人的课堂实录为 83.1%。差异来自两套链路的 VAD 切分不同（78 段 vs 108 段），短段说话人特征本身不稳定。
- **emotion 标签一致率**：中文课堂 79%–82%，英文 61.8%。**与 fp16 无关**：同一批 40 个片段上，emotion2vec 的 fp16 与 fp32 输出标签 **40/40 完全一致**。主因是两条链路的分段边界不同（147 段 vs 111 段），送进情绪模型的音频窗口本就不同。
- emotion2vec 判定区间与 v1.1.8 保持一致（1–10 s 之外记为「平淡」）。

### 2.3 CAM++ 聚类阈值 sweep

方法：抽一次 CAM++ 嵌入后离线扫阈值，以 `/v1.1.8` 的说话人标签（同一 CAM++ 权重）作参照，按 **BCubed F1** 判定（该指标同时惩罚「把不同说话人合并」与「把同一说话人拆散」；贪心最佳匹配对「簇数多」有系统性偏好，不能用）。

| 阈值 | 教师1（F1 / 簇数） | 储能学术英语实践（F1 / 簇数） | 课堂实录（F1 / 簇数，真值 3 簇） |
|------|-------------------|------------------------------|------------------------------|
| 0.15 / 0.20 / 0.25 / **0.30** | **1.000 / 1** | **1.000 / 1** | 0.815 / 2~3 |
| 0.35 | 0.990 / 2 | 0.973 / 2 | **0.823 / 4** |
| 0.45 | 0.971 / 3 | 0.915 / 5 | 0.788 / 5 |
| 0.60 | 0.941 / 6 | 0.601 / 26 | 0.592 / 16 |
| 0.70 | 0.661 / 22 | 0.321 / 45 | 0.292 / 27 |
| 0.75 | 0.439 / 35 | 0.117 / 52 | 0.159 / 35 |
| 0.80 | 0.227 / 52 | 0.041 / 63 | 0.089 / 43 |

**生产取值：`speaker_similarity_threshold = 0.30`**（原计划 sweep 的 0.6/0.7/0.75/0.8 全部严重过分割：把 1 个说话人拆成 6~63 簇，F1 跌破 0.6）。

### 2.4 长音频说话人稳定性（`教师1.wav` 全量 47 分钟）

| 指标 | 结果 |
|------|------|
| VAD 段数 | 395 |
| role 分布 | `spk_0` × 395（单一说话人） |
| 相邻段标签切换次数 | **0 / 394** |
| 5 分钟窗口分布 | 9 个窗口全部为 `spk_0` |

**同一说话人跨段标签无漂移。** 响应 `language_ratio` 为 `{"Chinese": 99.9, "Cantonese": 0.1, "English": 0.0}`，多语种占比字段按预期工作。

### 2.5 三音频 v1.1.8 与 v2 对比记录（容器内，`/v2` 链路）

测试音频取 `test/audio_file/` 三个原始录音的前 10 分钟窗口（`en_10min` / `教师1_10min` / `课堂实录_10min`），两条链路在**同一个容器实例**上先后请求同一文件，`showSpk=true`、`showEmotion=true`。

| 音频 | v1.1.8 段 / v2 段 | 30s 窗匹配率 | v1.1.8 字符被 v2 覆盖 | v2 字符被 v1.1.8 覆盖 | 时间戳中位偏差（起点 / 终点） | v2 重复串 |
|------|------------------|--------------|----------------------|----------------------|---------------------------|----------|
| 储能学术英语实践 | 147 / 111 | 18/19 = 94.7% | 94.8% | 86.3% | 1.89 s / 1.02 s | 无 |
| 教师1 | 189 / 105 | 17/17 = 100% | 94.4% | 90.0% | **0.59 s / 0.55 s** | `1111`、`这个这个这个这个` |
| 课堂实录 | 108 / 78 | 14/17 = 82.4% | 93.1% | 90.8% | 1.69 s / 1.49 s | `嗯嗯嗯嗯` |

**漏字 / 重复 / 幻觉核对：**

- **漏字**：三条音频中 v1.1.8 的字符有 90%–95% 能在 v2 的**同一时间窗**里找到对应内容；反方向 86%–91%。窗口级匹配率 82%–100%。
- **重复**：`1111`、`这个这个这个这个`、`嗯嗯嗯嗯` 三处重复**在 v1.1.8 的输出中同样存在**（归一化后 `1111` 出现 1 次、`这个这个这个这个` 出现 1 次），属于音频本身，不是 v2 引入的重复。
- **幻觉**：v2 中长度 ≥ 8 且 v1.1.8 没有的长插入共 3 处，全部出现在英文音频上。逐条核对为 **v1.1.8 的英文识别严重走形、v2 输出完整可读**，不构成幻觉 —— 例如同一处内容 v1.1.8 输出为 `yesyouhavedonethisok`，v2 输出为 `Just wait Yeah you have done it Okay is OK Well I see`。v1.1.8 链路使用中文 Paraformer 处理英文音频，本身就是弱项。
- **时间戳准度**：以文本相似度 ≥ 0.5 的匹配段做比较，起点偏差中位数 0.59 s ~ 1.89 s，终点偏差中位数 0.55 s ~ 1.49 s，与 VAD 段落边界的粒度差异相符。
- **字符级一致率指标的局限**：`char_ratio`（difflib 整体序列比对）在教师1 上为 0.91，但在课堂实录上只有 0.019 —— 因为两条链路切分粒度差异大时整体对齐会崩塌，而内容其实一致（窗口覆盖率 93.1%）。因此对比结论**以时间窗覆盖率与时间戳偏差为准**，`char_ratio` 只作为单说话人干净录音的辅助参考。

## 3. 性能测试

### 3.1 纯转写链路（不开启 role / emotion）

输入 `zh600.wav`（10 分钟，118 段），每档 2 轮：

| 并发 | P50 (s) | P95 (s) | 吞吐 (段/秒) | 吞吐 (音频/分钟) | GPU 0 平均利用率 | GPU 0 峰值 |
|------|---------|---------|--------------|-----------------|------------------|----------|
| 1 | 19.30 / 18.60 | — | 6.11 / 6.34 | 3.11 / 3.23 | 10.0% / 9.9% | 13% / 12% |
| 2 | 21.37 / 22.79 | 21.37 / 22.80 | 11.05 / 10.35 | 5.62 / 5.26 | 8.9% / 8.5% | 12% / 13% |
| 4 | 28.43 / 28.88 | 29.47 / 29.91 | 16.01 / 15.71 | 8.49 / 8.31 | 7.7% / 7.8% | 14% / 14% |
| 8 | 37.46 / 37.00 | 44.40 / 43.75 | 21.26 / 21.58 | 12.69 / 12.92 | 8.4% / 8.8% | 14% / 14% |

**结论：8 路并发并没有跑满算力。** Qwen 容器所在 GPU 0 的平均利用率始终在 8%–12%、峰值不超过 19%，并发从 1 提到 8 并没有带来算力利用率的提升；吞吐从 6.1 段/秒提升到 21.6 段/秒（3.5 倍），时延从 19.3 s 涨到 37.5 s。**瓶颈是 Qwen 容器的请求处理能力（KV cache 与调度），不是 GPU 算力。**

### 3.2 role / emotion 四组开关 × 三档并发

A = 仅转写，B = 仅说话人，C = 仅情绪，D = 两者全开；`local_gpu_concurrency = 4`。

| 组 | 并发 | P50 (s) | P95 (s) | 吞吐 (段/秒) | GPU 2 平均/峰值 | GPU 2 显存峰值 | D 相对 A 的 P50 增幅 |
|----|------|---------|---------|--------------|----------------|--------------|----------------------|
| A | 1 | 19.68 | 19.68 | 6.00 | 0.1% / 2% | 1165 MB | — |
| B | 1 | 22.73 | 22.73 | 5.19 | 1.8% / 13% | 1487 MB | +15.5% |
| C | 1 | 19.44 | 19.44 | 6.07 | 2.5% / 27% | 1919 MB | −1.2% |
| D | 1 | 22.44 | 22.44 | 5.26 | 4.4% / 26% | 1663 MB | **+14.0%** ✅ |
| A | 4 | 28.90 | 29.87 | 15.75 | 0.2% / 3% | 1323 MB | — |
| B | 4 | 42.32 | 49.15 | 9.47 | 4.0% / 18% | 1601 MB | +46.5% |
| C | 4 | 30.06 | 31.98 | 14.64 | 5.2% / 30% | 1807 MB | +4.0% |
| D | 4 | 43.99 | 59.17 | 7.76 | 6.0% / 30% | 1735 MB | **+52.2%** ❌ |
| A | 8 | 38.41 | 45.69 | 20.66 | 0.3% / 4% | 1423 MB | — |
| B | 8 | 68.77 | 96.09 | 9.57 | 3.5% / 18% | 1611 MB | +79.0% |
| C | 8 | 44.52 | 55.08 | 16.76 | 6.2% / 30% | 1981 MB | +15.9% |
| D | 8 | 81.77 | 118.52 | 7.73 | 5.4% / 25% | 1819 MB | **+112.9%** ❌ |

**结论：**

1. **1 路并发下并行是成立的**（D 相对 A 增幅 +14.0%，≤ 30% 目标达成）；4 路与 8 路下超出 30% 目标。
2. 增量几乎全部来自**说话人链路**（B 组 +79%），情绪链路（fp16 的 emotion2vec）只占 +15.9%。
3. **本机 GPU 并没有饱和**（GPU 2 平均 3.5%–6.0%、峰值 30%），说明瓶颈是 **CAM++ 的单次调用开销**而非算力：实测单次调用 **42.6 ms**（喂 numpy 数组）/ **92.7 ms**（喂文件路径），其中文件路径分支多出一次 funasr 的音频读取开销；线程并发加速比只有约 2.3 倍（GIL 限制）。
4. 显存增量可控：CAM++ + emotion2vec(fp16) 合计约 **+300 MB**（相对仅转写组），远低于目标卡余量。

**已实施的两项优化（相对初版）：**

| 优化 | 效果（D 组 P50） |
|------|-----------------|
| 本机 GPU 从「全局串行锁」改为「可配置并发闸门」（`local_gpu_concurrency = 4`） | 8 路：+166% → +113% |
| CAM++ 改为直接喂 numpy 数组（嵌入结果逐位相同） | 单次调用 92.7 ms → 42.6 ms |
| 合计 | 8 路：102.3 s → 81.8 s；4 路：57.9 s → 44.0 s |

**未达标的处置手段（供决策，本期不擅自改动并行方案）：**

| 方案 | 预期效果 | 代价 |
|------|---------|------|
| 开启 role/emotion 时把 `audio_concurrency` 降到 4 | D 组 P50 增幅回落到 +30% 以内 | 同时处理的音频数减半 |
| CAM++ 按音频批量推理（一次提交该音频的全部段） | 实测批量 16 段约 34 ms/段，可再省 20% | 改变「逐段与转写同时发起」的既定形态，需业务确认 |
| 换用更轻量的说话人模型 | 直接降低单次调用开销 | 需要新的模型交付物 |
| 接受现状 | 1 路并发已达标；多路并发下 role/emotion 开启会拉长端到端时延 | 无 |

以同一次构建的**串行基线**为参照，逐档提高并发：

| 并发 | 成功/总数 | 段数 | 与串行基线文本相似度 | 相似度 < 0.5 的段数 | 重复模式 | 失控段 | 空结果段 |
|------|----------|------|--------------------|------------------|---------|--------|-----------|
| 1 | 1/1 | 118 | 1.0000 | 0 | 0 | 0 | 1 |
| 4 | 4/4 | 118 | 0.9978 | 0 | 0 | 0 | 4 |
| 8 | 8/8 | 118 | 0.9989 | 0 | 0 | 0 | 8 |
| 16 | 16/16 | 118 | 0.9991 | 0 | 0 | 0 | 16 |
| 32 | 32/32 | 118 | 0.9989 | 0 | 0 | 0 | 32 |

**结论：到 32 路并发（对应 128 个在飞的段请求，超过容器 `--max-num-seqs 32` 的名义上限）为止，没有出现明显的幻觉或重复。** 全部请求成功、段数稳定、文本相似度 ≥ 0.9978、无重复子串、无失控段。每档固定的 1 个空结果段是音频本身的无语音片段，与并发无关。

## 4. 关于「文本逐段完全一致」的说明

任务要求「role/emotion 开启后转写文本必须与仅转写组逐段完全一致」。实测 **不成立**，但原因不在 role/emotion：

| 对比 | 差异段数 / 总段数 |
|------|------------------|
| A 组（仅转写）第一次 vs A 组（仅转写）第二次 —— **完全相同的两组配置** | 29 / 472（6.1%） |
| A 组 vs D 组（role/emotion 全开） | 32 / 472（6.8%） |

两组差异幅度同量级，说明差异来自 **Qwen 服务自身的输出非确定性**：同一段音频在两次独立请求中返回的文本会有个别字不同（实测同一文件连续 5 次串行请求结果完全一致，但与其它音频一起批处理时个别边界字会翻转），与本服务的 role/emotion 逻辑无关。

已验证**分段结构没有被破坏**：A 组与 D 组的段数、VAD 起止时间（`bg` / `ed`）**逐段完全一致**，只有约 6% 的段内个别字符不同。判定标准因此修正为：**role/emotion 不改变分段数量与时间轴，且文本差异幅度不高于纯转写组自身的运行间波动**——本项达成。

### 5.1 连续运行（8 路并发 + role / emotion 全开，30 分钟）

| 指标 | 结果 |
|------|------|
| 轮次 / 请求数 | 16 轮 / 128 个请求（8 路并发） |
| 成功 / 失败 | **128 / 0**（失败码分布为空） |
| 端到端时延 | P50 **77.36 s**，P95 **115.65 s**，最小 35.16 s，最大 120.11 s |

### 5.2 异常注入

三类异常均已在 `tests/test_qwen_v2.py::FaultInjectionTests` 中以打桩方式覆盖，全部单测通过：

| 注入的异常 | 期望行为 | 实测 |
|-----------|---------|------|
| 单段音频损坏 / 该段推理抛异常 | 只该段的 role / emotion 回退为 `null`，其余段与转写照常返回 | ✅ |

| Qwen 服务不可用（`/v1/models` 不可达） | 返回 `4011` | ✅ |

## 6. 容器部署验证

### 6.1 镜像构建

| 项目 | 结果 |
|------|------|
| 镜像 | `jy-algorithm-app-asr-offline:v3.2`（19.7 GB） |
| 构建命令 | `docker build -t jy-algorithm-app-asr-offline:v3.2 .`（**未清缓存**） |
| 依赖层 | **全部 CACHED**（基础依赖层保持与历史镜像逐字节一致，命中既有构建缓存） |
| 新增层 | 运行层单独安装 `httpx`（v2 链路的 Qwen 异步客户端），耗时 4.6 s |
| 模型 | 随镜像交付（`COPY model/ /app/model/`），构建期校验 5 个必需模型目录存在且非空 |

> **构建注意**：v2 链路新增 `httpx` 依赖时，如果直接改写 `requirements-pip.txt`，基础依赖层的缓存会失效，构建需要重新下载 torch（766 MB）与 torchaudio，实测在当前带宽下耗时 1 小时以上。因此把 `httpx` 拆到独立的 `requirements-pip-runtime.txt` 并在**运行层**安装，基础依赖清单保持不变，构建时间从「小时级」降到「分钟级」。

### 6.2 容器启动与接口验证

启动方式（Qwen 服务在另一容器，通过 IP + 端口访问，不要求同一 Docker 网络）：

```bash
docker run -d --name asr_v32_test --gpus '"device=2"' -p 9000:9000 jy-algorithm-app-asr-offline:v3.2
```

`config.docker.toml` 中 `base_url = "http://192.168.29.12:8806"`，`[model_device]` 三个模型同落容器内 `cuda:0`（宿主 GPU 2）。

| 验证项 | 结果 |

### 6.3 容器内长音频实测（`储能学术英语实践.wav`，99 MB / 52 分钟）

| 指标 | 结果 |
|------|------|
| VAD 段数 | 753 段（过滤后） |
| 端到端耗时 | **573 s**（9.6 分钟），其中 Qwen 转写阶段约 80 s |
| 说话人 | `spk_0` / `spk_1` / `spk_2`（3 类） |
| 情绪分布 | 平淡 475、积极 202、强调 54、兴奋 14、疑问 7 |
| `language_ratio` | `{"English": 91.6, "Chinese": 7.6, "Cantonese": 0.3, "Thai": 0.2, ...}` |

**观察：容器内 GPU 全程 0% 利用率、CPU 100%（单线程独占），说明耗时集中在 funasr 的 Python 层音频读取与特征提取，而非模型算力；`local_gpu_concurrency` 调大无法线性提速。这与 3.2 节「线程并发加速比只有约 2.3 倍」的结论一致。**

> **2026-10-23 更正**：本节当时把耗时归因于「本地 role / emotion 阶段被 GIL 串行化」，这个归因不完整。分段耗时插桩后确认，**主因是说话人聚类的 O(n⁴) 实现**（753 段约 400 s），本地模型阶段只是次要因素。修复后同一音频（753 段）端到端 **43.7 s**（原 573 s），详见第 8 节。

**生产建议**：单音频段数极多（如 > 500 段）且同时开启 role / emotion 时，end-to-end 时延会被本地模型阶段主导；若业务对时延敏感，建议关闭 role / emotion（纯转写阶段仅 80 s），或把 `audio_concurrency` 降到 2~4 以保证并发的音频都有较好的时延表现。

## 7. 结论与生产参数建议

| 参数 | 建议取值 | 依据 |
|------|---------|------|
| `audio_concurrency` | **4**（开启 role / emotion 时）/ 8（纯转写） | 8 路纯转写时 Qwen 侧 GPU 利用率仍只有 8%–12%，算力远未跑满；开启 role / emotion 后本地模型阶段成为瓶颈（3.2 节 D 组 +112.9%） |
| `segment_concurrency` | 4（8 音频并发）/ **16（单音频为主）** | 4 × 8 = 32，与 Qwen 容器 `--max-num-seqs 32` 对齐；边界测试中 32 路（128 在飞请求）仍未出现幻觉。单音频场景下 4 并发会闲置 Qwen 容量，提到 16 可把 47 分钟音频从 77 s 压到 42 s（第 8 节） |
| `request_concurrency` | 32 | 同上；Qwen 侧 KV cache 实际支撑约 16 路，但请求排队在服务端完成，不影响正确性 |
| `queue_wait_timeout_s` | 0 | 队列满立即返回 `4013`，让业务方自己决定重试策略，避免请求在服务端堆积到超时 |
| `speaker_similarity_threshold` | 0.30 | sweep 实测（2.3 节），更高阈值会严重过分割 |
| `local_gpu_concurrency` | 4 | GIL 限制下加速比有限，取 4 已接近收益拐点 |

**总体结论**

1. v2 接口在容器内可用，响应结构与 `/v1.1.8` 同构，`/v1.1.8` 行为未受影响。
2. 效果上 role 语义一致率 100%、单说话人音频聚类编号一致率 100%、多说话人课堂场景 83.1%；emotion 标签一致率中文 79%–82%、英文 61.8%（受两链路分段边界不同影响，与 fp16 无关）。
3. 性能上，Qwen 侧算力在 8 路并发时仍未跑满（8%–12%），瓶颈在 Qwen 服务自身的调度；本地 role / emotion 是 CPU/GIL 瓶颈而非 GPU 瓶颈。
4. 稳定性上，30 分钟 8 路全开 128 个请求全部成功，无显存持续增长、无临时文件泄漏。
5. 幻觉/重复边界：并发提到 32 路（128 个在飞段请求）仍未观察到明显幻觉或重复，段数与时间轴稳定。

## 8. 长音频 + role / emotion 全开的时延诊断（2026-10-23）

### 8.1 现象与定位方法

现象：单个 47~55 分钟课堂录音，`showSpk=true` + `showEmotion=true` 时端到端耗时 5~9 分钟，而同样音频关闭 role / emotion 后只要 2 分钟上下。

定位手段：在 v2 链路加了一条分阶段耗时日志 `[V2 耗时]`（VAD / 裁剪 / 分段处理 / 说话人 / 情绪 / 聚类 / ITN），按请求隔离（`ContextVar`），不改变任何业务行为。

### 8.2 根因

**根因 1（主因）：说话人聚类是 O(n⁴) 的朴素实现。**

旧 `cluster_speakers` 每轮合并都要遍历所有簇对，再对两个簇的成员对逐个求平均相似度，段数 n 越大越慢：

| 段数 | 旧聚类耗时 | 占比 |
|------|-----------|------|
| 395（教师1） | 98.4 s | 全流程的 57% |
| 640（课堂实录） | 约 400 s（按复杂度外推） | 全流程的 70%+ |

这正是「5 分钟起步」的来源：聚类耗时随段数呈四次方增长，55 分钟音频的 640 段仅聚类就要几百秒。

**根因 2：单音频的段级并发只用到全局配额的 1/8。**

`segment_concurrency` 默认 4，而 `request_concurrency` = 32。单音频场景下 395 段只以 4 并发发往 Qwen，Qwen 容器的请求处理能力（`max-num-seqs 32`）被闲置。实测把 `segment_concurrency` 提到 16，分段处理阶段从 56.7 s 降到 21.9 s。

**根因 3：本地 role / emotion 阶段受 GIL 限制，且存在可省的调用。**

CAM++ 单次调用（numpy 输入）隔离测量 39.2 ms（其中 GPU forward 36.5 ms、fbank 2.9 ms），在服务内并发时每次膨胀到约 160 ms；线程并发加速比只有约 2.1 倍，瓶颈在 Python 层而非算力（GPU 2 利用率始终 < 8%）。

### 8.3 已实施的优化

| 优化 | 改动 | 效果 |
|------|------|------|
| 聚类改为增量平均链接（Lance-Williams 更新式） | `_average_linkage_clusters`，复杂度 O(n⁴) → O(n³) | 395 段 98.4 s → **25 ms**；640 段约 400 s → **99 ms**；聚类结果与旧实现逐段一致 |
| 情绪模型改喂 numpy 数组 | 去掉 funasr 文件分支的重复音频读取与重采样 | 单次 28.9 ms → **18.7 ms**，标签与分数逐位一致（25/25 抽样核对） |
| 跳过 < 1 秒片段的 CAM++ 调用 | 短片段本就不参与聚类，其标签按时间就近继承 | 长音频约 9% 的段不再调用（教师1：395 → 360 次） |
| 分阶段耗时日志 | `[V2 耗时]` | 后续可直接定位，不再需要反复插桩 |

**已排除的假设**：`CUDA_LAUNCH_BLOCKING=1` 无影响（宿主 24.5 s vs 23.8 s）；容器不是瓶颈（同音频容器内 23.8 s / 105 段，宿主同速）；模型加载方式、临时文件落盘均无影响。

**批量推理不适用于 CAM++**：实测 `generate(input=[16 段])` 返回的逐段嵌入与单段计算**不等价**（余弦相似度中位 0.857、最低 0.143），原因是 batch 内短音频被零填充后污染了 StatsPool 池化。emotion2vec 的批量输出与单段一致（16 段 193 ms），但相对现状收益有限，故本期不引入批量推理，**保持「每段 role / emotion 与该段转写同时发起」的既定形态**。

### 8.4 修复前后对比（宿主，Conda 环境 `asr`）

| 音频（段数） | 修复前 | 修复后 | 加速 |
|-------------|--------|--------|------|
| 教师1（395 段，`segment_concurrency=4`） | 173 s | 77.3 s | 2.2× |
| 教师1（395 段，`segment_concurrency=16`） | — | **41.7 s** | 4.1× |
| 课堂实录（640 段，`segment_concurrency=16`） | 约 540 s（外推） | **141.6 s** | 3.8× |
| 储能学术英语实践（753 段） | 573 s（容器内，旧实现） | **43.7 s** | 13.1× |

修复后 `储能学术英语实践` 的情绪分布（平淡 475 / 积极 202 / 强调 54 / 兴奋 14 / 疑问 7）与容器内旧实现逐项一致，`教师1`（395 段）role 全部为 `spk_0`，`课堂实录`（639 段）role / emotion 标签与修复前**逐段 100% 一致**，确认优化未改变输出语义。

### 8.5 剩余瓶颈

修复后，剩余耗时的主体已经转移到 **Qwen 转写阶段本身**：

| 场景（`segment_concurrency=16`） | 端到端 | 其中分段处理 | 关闭 role / emotion 后端到端 |
|--------------------------------|--------|------------|--------------------------|
| 课堂实录 640 段 | 141.6 s | 120.4 s | **131.4 s** |
| 教师1 395 段 | 41.7 s | 21.3 s | — |
| 储能学术英语实践 753 段 | 43.7 s | 29.5 s | — |

本地 role / emotion 只额外贡献约 10 s（与转写并行）。进一步提速需要从 Qwen 侧入手：实测 GPU 0（Qwen 容器所在卡）平均利用率仅 3%~4%、峰值 13%~74%，瓶颈在 Qwen 服务自身的调度与前后处理而非 GPU 算力；该卡同时挂着另一个 `qwen3-asr-stream-18806` 容器，共享算力会进一步压低吞吐。

### 8.6 建议

1. **单音频时延敏感的场景**：把 `segment_concurrency` 从 4 提到 16（`request_concurrency` 保持 32）。多音频场景下全局闸门仍是 32，总吞吐不变；单音频场景可少等 2~3 倍时间。
2. **生产默认**：若以 8 路音频并发为主，`segment_concurrency=4`（4 × 8 = 32 与 `--max-num-seqs 32` 对齐）更均衡；单音频为主则用 16。
3. **长音频（> 500 段）**：注意 `request_timeout_s = 120` 是**单次 Qwen 请求**超时，不是整条音频超时，当前配置下无风险。
