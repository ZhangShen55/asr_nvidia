# 固定 VAD 16 Worker、16 路并发复测报告

## 1. 测试配置

- 日期：2026-10-27
- 接口：`POST /v2/seacraft_asr`
- 音频：`test/audio_file/教师1.aac`
- 音频时长：3303.28 秒（约 55.05 分钟）
- 并发：16 路完整音频
- `showSpk=true`，`showEmotion=true`
- VAD：CPU，服务启动时固定预热 16 个 worker
- 本地模型：CAM++ 4 实例、emotion2vec 4 实例，全部在 `cuda:0`
- Qwen-ASR：`127.0.0.1:8806`，测试期间保持运行

固定池配置：

```toml
vad_pool_size = 16
vad_pool_max = 16
```

每个成功请求均完成 535 个 VAD 段，最终返回 518 个文本段。服务端没有出现 VAD 排队超时。

## 3. 阶段耗时

16 个成功请求的服务日志统计：

- VAD 阶段：中位数 39.144 秒，范围 15.889～47.058 秒。
- 分段处理：中位数 548.728 秒。
- CAM++：中位数 105.796 秒/请求。
- emotion2vec：中位数 41.866 秒/请求。
- 总处理耗时：中位数 590.999 秒。

## 4. 固定池状态验证

服务启动日志确认 16 个核心 worker 全部预热完成：

```text
[VAD 池] 启动：设备=cpu 常驻=16 上限=16
worker#0 ... worker#15 预热完成
```

测试期间状态始终为：

```json
{
  "workers": 16,
  "pool_size": 16,
  "pool_max": 16,
  "busy": 0,
  "waiting": 0
}
```

没有出现扩容 worker，也没有出现 worker 异常退出。CAM++ 和 emotion2vec 均为 4/4 实例加载成功，`failed_instances=0`，GPU 0 未发生 OOM。

## 5. 与 32 路动态扩容结果对比

| 指标 | 固定 16 VAD / 16 路 | 动态上限 32 VAD / 32 路 |
| --- | ---: | ---: |
| 成功率 | 16/16（100%） | 18/32（56.25%） |
| 墙钟时间 | 686.477 秒 | 1842.044 秒 |
| 音频吞吐 | 1.398 路/分钟 | 0.586 路/分钟 |
| VAD P50 | 39.144 秒 | 约 951.972 秒 |
| VAD 排队失败 | 0 | 14 |

固定 16 路的音频吞吐约为 32 路结果的 2.38 倍，VAD 阶段明显降低。32 路同时进入时，CPU 线程争用和请求排队使 VAD 阶段严重变慢；继续扩大 `pool_max` 不能带来吞吐提升。

## 6. 结论

当前场景验证了以下运行方式：

```text
上游音频并发量 = vad_pool_size = 16
vad_pool_max = vad_pool_size
```

一个 VAD worker 处理一份完整音频，固定 16 个 worker 作为有效热加载池，不使用动态扩容，可以稳定完成 16 路完整音频并发。建议后续将上游 `audio_concurrency` 同步限制为 16，避免超过 VAD 有效并发后产生隐藏排队。

本轮测试结束后已关闭 8084，Qwen-ASR 的 8806 端口仍在监听。
