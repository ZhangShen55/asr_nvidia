# VAD CPU 进程池完整音频效率报告（2026-10-26）

## 1. 测试结论

在 Conda `asr` 环境中，使用 v2 `/v2/seacraft_asr` 对完整长音频进行 2/4/8/16/32 路并发测试，`showSpk=false`、`showEmotion=false`。8084 后端已在测试结束后关闭，Qwen ASR 8806 保持运行。

- 五档共处理 62 份完整音频、34,395 个 VAD 段，全部成功，失败数为 0。
- 峰值吞吐出现在 c4：41.70 段/s；c8 基本持平，为 41.46 段/s。
- c16 降至 35.00 段/s，c32 降至 24.79 段/s；并发继续增加不能提升端到端吞吐。
- Qwen 引擎没有形成排队瓶颈：所有档位 `waiting=0`，KV cache 峰值最高 8.1%，平均队列时延为 0。
- 结果支持当前 VAD CPU 进程池配置可用，但在 16 路以上需要关注 CPU 调度和前端切段开销。

- 纯标点段、段首标点段、空段、特殊 token 残留均为 0。

- Qwen 的 `finished_reason=length` 统计随档位为 1/1/1/2/3，属于少量生成长度截断；本轮未启用说话人和情绪链路。

## 6. 临时文件观察

本轮服务实现使用段 clip 惰性创建、转写完成立即删除，且每个音频的在途段数受段并发 4 限制。测试结束并关闭 8084 后，未发现残留的段 clip 文件。

压测期间 `/tmp` 中出现的约 1.69 GB `v2_*` 文件是 32 份上传音频的源文件，不是段 clip，不能作为段文件峰值。由于本轮未以独立采样器记录段 clip 的瞬时峰值，报告不把该源文件占用冒充为 clip 峰值；需要精确峰值时应在下一轮用文件名过滤器按 100~200 ms 周期采样 `tmp*`/clip 文件，并排除 `v2_*` 上传源文件。

## 7. 结论与建议

1. 当前 8 个 CPU VAD worker 在 c4~c8 已达到本机端到端最佳区间，建议生产默认保持 `vad_pool_size=8`，不要仅为追求更高并发把常驻池直接扩大到 16。
2. c16/c32 的吞吐回落而 Qwen 仍无排队，说明后续优化重点应放在本服务的音频预处理、VAD 调度、段裁剪和 Python 编排，而不是提高 Qwen 的 `max-num-seqs`。
3. 8 worker 每个约 2.2~2.5 核，容器建议至少 24~32 核；若只有 16 核，建议将 `vad_pool_size` 降到 4。
4. 保持 Qwen 8806 独立运行；本轮 8084 已关闭，重新启动后可复用上述命令和结果目录。
