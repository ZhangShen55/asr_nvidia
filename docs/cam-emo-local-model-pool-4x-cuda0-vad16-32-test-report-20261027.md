## 3. 阶段耗时与模型状态

成功请求的服务日志显示：

- VAD 阶段中位数约 951.972 秒，除一个较早完成的请求外，大多数请求都在约 15.9 分钟后完成 VAD。
- 分段处理阶段中位数约 748.100 秒。
- CAM++ 推理累计耗时中位数约 115.033 秒/请求，emotion2vec 中位数约 35.476 秒/请求。
- 典型成功请求总耗时约 1675～1723 秒。

测试结束状态：

- VAD：16 个 worker，`busy=0`，`waiting=0`。
- CAM++：4/4 实例加载成功，全部在 `cuda:0`，`failed_instances=0`。
- emotion2vec：4/4 实例加载成功，全部在 `cuda:0`，`failed_instances=0`。
- GPU 0 显存约 28.9 GB / 49.1 GB，未发生 OOM；测试期间采样到 GPU 利用率约 66%。
- GPU 1、GPU 2 未承载这两个模型。

## 4. 失败原因

本轮 14 个失败请求均对应服务日志中的：

```text
[V2] VAD 阶段异常: VAD 切分排队超时，请稍后再试
```

失败集中发生在 10:24:49～10:25:00。没有发现 CAM++、emotion2vec 加载失败、CUDA OOM 或 Qwen-ASR HTTP 错误。

因此，本轮的主要卡点仍然是 **VAD 进程池排队**。将 `vad_queue_timeout_s` 与 `vad_call_timeout_s` 拆开并提高到 600 秒，避免了原先 120 秒配置下的过早超时，但没有消除 32 路完整长音频同时进入 VAD 时的排队压力。

## 5. 与上一轮基线对比

上一轮同为 32 路、4+4 模型实例、全部落在 `cuda:0` 的结果为成功 15/32，墙钟时间 757.084 秒，失败主要也是 VAD 超时。

本轮成功数增加到 18/32，但墙钟时间增加到 1842.044 秒，且仍有 14 个 VAD 排队失败。说明本次改造改善了可完成请求数，却没有带来 32 路整体效率提升；16 个常驻 VAD worker 在完整 55 分钟音频上仍不足以支撑 32 路同时进入。

## 6. 结论与建议

1. CAM++/emotion2vec 的 4 实例本地模型池工作正常，全部固定在 `cuda:0` 的配置已验证，不是本轮失败原因。
2. 当前 32 路瓶颈在 CPU VAD 长音频处理和 VAD 队列，不在 GPU 模型池。
3. 单纯继续增加超时只会让请求等待更久，不能提升吞吐；需要降低单份完整音频的 VAD CPU 成本或控制进入 VAD 的音频并发。
4. 后续建议先限制完整音频 VAD 的有效并发，或进一步优化/分片 VAD；同时测量每个 VAD worker 的线程数，避免 16 个进程各自创建大量推理线程造成 CPU 争用。完成这两项后再评估是否将 `vad_pool_size` 提到 32。

测试结束后已关闭本次 8084 服务，Qwen-ASR 的 8806 端口仍在监听。
