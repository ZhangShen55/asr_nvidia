# Qwen3-ASR v2 并发压测报告（2026-10-23）

本报告回答两个问题：

1. 按「方案 A」把 Qwen 服务改成 **4 前端 + 单引擎** 后，`/v2/seacraft_asr` 能不能把 GPU 跑起来；
2. 在 `showSpk` / `showEmotion` 关闭与全开两种模式下，4/8/16/32 并发的效率、效果、幻觉与标点表现。

## 1. 测试环境

| 项目 | 配置 |
|------|------|
| Qwen 容器 | `qwen3-asr-0.6b-8806`（`qwenllm/qwen3-asr:latest`，vLLM 0.14.0） |
| 容器启动参数 | `--served-model-name Qwen3-ASR-0.6B --dtype bfloat16 --max-model-len 1024 --max-num-seqs 128 --max-num-batched-tokens 16384 --gpu-memory-utilization 0.45 --api-server-count 4` |
| 旧容器 | `qwen3-asr-0.6b-8806.bak`（`max-model-len 4096`、`max-num-seqs 32`、`enforce-eager`，已停止，可回滚） |
| 本服务 | `refactor/adapt-qwen-asr`，conda 环境 `asr`，uvicorn 单实例，`CUDA_VISIBLE_DEVICES=0`，端口 8083 |
| 本地模型 | VAD ×4 实例、CAM++ ×1、emotion2vec ×1，全部落 GPU 0 |

| 压测音频 | `test/audio_file/` 中 39 个 ≥10 分钟的完整音频文件 |

> 本次部署只在宿主机 Docker 层面改容器，未改动、未构建本项目的镜像。

### 1.1 压测数据集

- 从 `test/audio_file/` 中取全部 ≥10 分钟的音频，共 41 个；
- 用 `ffmpeg volumedetect` 复核后剔除 2 个**静音录音**（`mean_volume` 分别为 -65.9 dB、-64.2 dB，VAD 切出 0 段），最终 **39 个**文件进入音频池；
- 每个并发档位取音频池的前 N 个**完整**文件（不截断），因此 c4 的 4 个文件同时出现在 c8/c16/c32 中，可做配对比较；
- 单文件时长 45~65 分钟，单档位音频总量 c32 约 32 小时。

## 2. 容器参数核对

启动日志中与本次目标直接相关的三行：

```
Available KV cache memory: 16.02 GiB
GPU KV cache size: 149,936 tokens
Maximum concurrency for 1,024 tokens per request: 146.42x
```

- KV cache **149,936 tokens** > 128 × 1024 = 131,072 的最坏需求，`request_concurrency = 128` 不会因 KV 不够而排队；
- 已去掉 `--enforce-eager`，CUDA graph 正常捕获（mixed 35 个 + decode 19 个，耗时 7 秒、占用 0.30 GiB）；
- `--api-server-count 4` 生效，日志中出现 `ApiServer_0..3` 四个独立前端进程，破 GIL。

### 3.3 关键判读

1. **Qwen 引擎完全没吃饱。** 两种模式下 `waiting` 全程为 0，`running` 峰值只有 11~16（上限 128），KV cache 峰值 0.7%~1.6%（16 GiB 只用了不到 0.26 GiB）。Qwen 容器 CPU 峰值也只有 3.1~3.7 核，远低于 4 前端的理论上限约 4 核。
2. **吞吐与并发档位基本无关。** c4→c32 并发扩大 8 倍，纯转写吞吐 26.1→24.5 段/s 反而略降；开 role/emotion 后 9.4→6.4 段/s 下降 31%。说明限制不在 Qwen，在本服务侧。
3. **GPU0 利用率不代表算力饱和。** GPU0 平均只有 8.6%~26.3%，峰值却能打到 71%~100%——这是小模型 + 短 kernel 的典型波形，与 §4 的瓶颈定位一致。

## 4. 瓶颈定位

从服务日志 `api.routes.asr_qwen_common` 的分阶段耗时聚合：

### 4.1 showSpk/showEmotion 全关（64 份文件、36,956 段）

| 阶段 | 累计占比 | 单段耗时 |
|------|---------|---------|
| **VAD** | **83.2%** | 357.9 ms |
| 分段处理（Qwen 转写） | 14.6% | 62.7 ms |
| 音频裁剪 | 1.1% | 4.6 ms |
| ITN | 1.1% | 4.7 ms |

**VAD 占掉 83% 的时间，是唯一的瓶颈。** 原因在 `core/vad.py` 的实例池设计：FSMN-VAD 实例带可变状态缓存，为防并发数据错乱，用 `vad_concurrency = 4` 的实例池，**每个实例同一时刻只跑一个请求**；而一个请求 = 一整个 45~65 分钟音频，单文件 VAD 实测 44~123 秒。c4 恰好 4 个文件配 4 个实例（不排队），c8 起 8~32 个文件挤 4 个实例，吞吐就压平在 26 段/s。

### 4.2 showSpk/showEmotion 全开（60 份文件、34,463 段）

| 阶段 | 累计占比 | 单段/单次耗时 |
|------|---------|-------------|
| **分段处理（Qwen + CAM++ + emotion 合计）** | **76.4%** | 1483.6 ms/段 |
| VAD | 23.1% | 448.0 ms/段 |
| 音频裁剪 | 0.3% | 6.0 ms |
| ITN | 0.2% | 4.6 ms |
| ├─ CAM++ 嵌入 | 18.3% | **430.5 ms/次** |
| └─ emotion2vec 推理 | 7.2% | 169.8 ms/次 |
| 说话人聚类 | — | 120.6 ms/文件 |

CAM++ 每个 ≥1 秒的片段调用一次（每文件 355~690 次），单次 430.5 ms，与 Qwen 段转写走同一个 `_process()` 任务，二者被 `asyncio.gather` 绑在一起，因此 `segment_ms` 把三者合并计入。全开时端到端变慢约 **2.8~4.5 倍**，GPU0 平均利用率反而从 19%~26% 掉到 8.6%~12.2%——**本地推理拖住了喂给 Qwen 的节奏**。

- **纯标点段、段首标点段全部为 0**，8 档位 75,315 个段无一例外，标点卫生规则在 128 路在飞请求下仍然稳定生效；
- 所有 8 档位**零请求失败**，无 HTTP 错误、无 4012、无 4008；
- 单文件请求级零失败，但 Qwen 客户端有 3 次**段级重试**（17:39:39、18:26:37、18:29:37），均为 `httpx.TimeoutException / TransportError` 且第 1 次重试即成功（占 36,956 + 34,463 = 71,419 个段请求的 0.004%），未触发 `retry_count = 1` 的上限，也未影响任何文件的最终结果；
- 句末标点率 0.81~0.95（c4 偏低是分母小、4 份文件语种/内容不同所致，不是档位效应）；段均字数在所有档位都是 21.0，稳定。

### 5.2 幻觉与重复长文本

**同一段音频（`思想道德与法治_2424101_2424102_董金平`）在 c16 和 c32 各触发了一次典型的生成死循环**，其余档位完全正常：

| 档位 | 位置 | 生成文本长度 | 表现 |
|---|---|---|---|
| no-role c16 | 段 #315，1715.85~1721.80s | **1863 字符** | 「最小S零，这个这个这个这个，这个这个这个，……」后接长串「这个」 |
| no-role c32 | 段 #315，1715.85~1721.80s | **1863 字符** | 同上，同一段被复现 |
| both c32 | 同段 | 出现 9 字符级连复读 | 「这个这个这个，这个这个这个这个，……」 |

引擎 `finished_reason=length` 计数与之对应：

| 档位 | no-role 截断数 | both 截断数 |
|---|---|---|
| c4 | 0 | 2 |
| c8 | 0 | 2 |
| c16 | **1** | 3 |
| c32 | **2** | **4** |

**判读：**

- 该段音频本身正常（c4/c8 同一份音频转写完全正常，无复读）；
- 这是 Qwen3-ASR 在该 VAD 段上的**偶发生成幻觉**，触发上限 1024 token 后被 vLLM 掐断，没有继续烧 token；
- 触发频次 **1~4 次 / 每档位 2,700~17,300 段**，约 0.01%~0.02%；
- c16/c32 触发次数略高于 c4/c8，但样本量不同（c32 的段数是 c4 的 6.4 倍），**归一化后频次反而略低**，因此没有证据表明并发会显著提高幻觉率；
- 各档位「长复读段」2~20 段，占对应段数的 0.02%~0.12%，其中大部分是音频里真实重复的口语（如「温度载荷，温度载荷，温度载荷」），非模型幻觉。

## 6. 结论与建议

### 6.1 本次部署目标是否达成

| 目标 | 结果 |
|---|---|
| Qwen 侧支持 128 路在飞请求 | **达成**：KV 149,936 tokens > 131,072 需求，running 峰值 16、waiting 0、队列时延 0s |
| 前端突破 GIL | **达成**：4 个独立 ApiServer 进程，CPU 峰值 3.1~3.7 核 |
| 32 路并发零失败 | **达成**：8 档位共 118 份完整音频请求，失败 0 |
| 标点卫生 | **达成**：纯标点段、段首标点段全部为 0 |
| GPU 利用率提升 | **部分**：GPU0 峰值可达 100%，但平均仅 8.6%~26.3% |

### 6.2 当前真实的限制因素

**Qwen 不是瓶颈，本服务侧的本地推理才是：**

- 纯转写：`vad_concurrency = 4` 限制了 4 个 VAD 实例，每个实例串行跑一个 45~65 分钟音频，占总耗时 83.2%；
- 全开 role/emotion：CAM++ 单次 430.5 ms + emotion2vec 169.8 ms 与 Qwen 段转写绑在同一个 `_process()` 任务里，占分段处理的 76.4%；
- **加 Qwen 的 `--api-server-count`、加 KV cache、加并发档位都救不回来**，因为喂给 Qwen 的段本来就慢。

### 6.3 可以做的优化方向（均未实施，需另开 change）

| 方向 | 预期收益 | 代价 / 风险 |
|---|---|---|
| **音频先 VAD、再切窗口并发跑 VAD**，而不是整文件交给一个实例 | 纯转写吞吐有大幅空间（VAD 占 83.2%） | 需改 `core/vad.py` 的实例池语义；FSMN-VAD 的状态缓存要确认分块边界是否等价 |
| **VAD 模型本身并行化**（FunASR streaming 模式按 chunk 调用） | 同上 | 需验证切点是否一致，涉及切分质量 |
| **CAM++ 改批量推理** | CAM++ 占 18.3% | 已在历史测试中验证**批量结果不等价**，不建议 |
| **把 CAM++/emotion2vec 拆到独立进程**（各自独立 GIL） | 本地推理不再与主链路抢 GIL | 显存翻倍、IPC 开销，需要新进程模型 |
| 调低 `max_model_len` 已由 4096 → 1024 生效 | 幻觉段在 1024 token 被截断，不再烧满 4096 | 已生效，无需动作 |

## 7. 复现方式

```bash
# 1) 起 Qwen（方案 A，固定 GPU0）
sudo docker run -d --name qwen3-asr-0.6b-8806 \
  --gpus '"device=0"' -p 8806:8000 \
  -v /mnt2/model_zoo/llm_model/Qwen3-ASR-0.6B:/models/Qwen3-ASR-0.6B:ro \
  --entrypoint qwen-asr-serve qwenllm/qwen3-asr:latest \
  /models/Qwen3-ASR-0.6B --host 0.0.0.0 --port 8000 \
  --served-model-name Qwen3-ASR-0.6B --dtype bfloat16 \
  --max-model-len 1024 --max-num-seqs 128 --max-num-batched-tokens 16384 \
  --gpu-memory-utilization 0.45 --api-server-count 4

# 2) 起本服务（config.toml：request_concurrency=128、audio_concurrency=32）
CUDA_VISIBLE_DEVICES=0 CONFIG_PATH=./config.toml \
  python -m uvicorn main:app --host 0.0.0.0 --port 8083 --workers 1

# 3) 跑压测（每档位从音频池取前 N 个完整文件，不截断）
python scripts/bench_qwen_v2_concurrency.py \
  --concurrency 4,8,16,32 --mode no-role --out-dir /tmp/bench_qwen/phaseA
python scripts/bench_qwen_v2_concurrency.py \
  --concurrency 4,8,16,32 --mode both   --out-dir /tmp/bench_qwen/phaseB

# 4) 跑效果分析（幻觉重复、标点卫生、连贯性）
python scripts/analyze_qwen_v2_quality.py \
  --bench-dir /tmp/bench_qwen/phaseA --out /tmp/bench_qwen/phaseA_quality.json
python scripts/analyze_qwen_v2_quality.py \
  --bench-dir /tmp/bench_qwen/phaseB --out /tmp/bench_qwen/phaseB_quality.json
```

压测脚本同时采集 GPU 利用率/显存（200 ms）、Qwen 引擎 `running`/`waiting`/KV 使用率（1 s）、容器 CPU 占用（2 s），并把每份响应的完整 JSON 落盘，便于逐段复核。

## 8. 已知限制

- 每个档位只跑 1 轮；跨档位的文本相似度差异包含采样随机性，不构成统计显著性结论；
- 两个静音录音被排除在音频池外（否则会占用并发槽、产出 0 段）；
- 未验证 `instance_count > 1` 的多进程形态；
- 本报告不涉及镜像构建与部署，容器参数改动只在宿主机 Docker 层面生效。
