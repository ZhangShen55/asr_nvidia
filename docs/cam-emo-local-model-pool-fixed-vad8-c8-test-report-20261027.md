# 固定 VAD 8 Worker、8 路并发复测报告

## 1. 配置

- 音频：`test/audio_file/教师1.aac`，3303.28 秒
- `showSpk=true`，`showEmotion=true`
- `vad_pool_size=8`，`vad_pool_max=8`，CPU VAD，启动时固定预热
- CAM++ 4 实例、emotion2vec 4 实例，全部落在 `cuda:0`
- 上游 `audio_concurrency=8`
- Qwen-ASR `8806` 保持运行，测试服务端口 `8084`

## 2. 结果

| 指标 | 8 路结果 |
| --- | ---: |
| 成功/失败 | 8/8，0 失败 |
| 总墙钟时间 | 358.891 秒 |
| 请求耗时 P50 | 347.461 秒 |
| 请求耗时 P95 | 358.885 秒 |
| 请求耗时最大值 | 358.885 秒 |
| 音频吞吐 | 1.337 路/分钟 |
| 输出段吞吐 | 11.547 段/秒 |

每个请求完成 535 个 VAD 段，最终返回 518 个文本段。VAD 没有排队超时，模型没有加载失败或 OOM。

## 3. 与 4 路对比

| 指标 | 4 路 | 8 路 | 8/4 |
| --- | ---: | ---: | ---: |
| P50 | 188.462 秒 | 347.461 秒 | 1.844x |
| 服务阶段总耗时中位数 | 157.485 秒 | 316.826 秒 | 2.012x |
| VAD 阶段中位数 | 18.347 秒 | 21.163 秒 | 1.154x |
| 分段处理阶段中位数 | 136.036 秒 | 290.251 秒 | 2.133x |

VAD 只小幅变慢，主要增长来自分段处理阶段。8 路服务阶段中位数约为 4 路的两倍，端到端 benchmark P50 为 1.844 倍，结论上属于接近翻倍。

## 4. 对 CAM++/emotion2vec 实例数的判断

当前配置中，CAM++ 和 emotion2vec 虽然各有 4 个实例，但代码还有一个共享的全局限制：

```toml
local_gpu_concurrency = 4
```

这个信号量同时限制 CAM++ 和 emotion2vec 的 GPU 推理调用总数，不是每个模型各 4 路。因此 8 路请求会在本地 GPU 推理阶段形成等待；增加模型实例数但不提高 `local_gpu_concurrency`，不会把有效并发提升到 8。

本轮的结果可以确认 **4 路本地 GPU 推理并发是主要限制因素之一**，但不能只归因于“模型副本数为 4”：当前实际生效的是“CAM++/emotion2vec 共享 4 路 GPU 推理并发”。VAD 不是本轮翻倍原因。

## 5. 结论

如果目标是让 8 路的 P50 不接近 4 路的两倍，需要成组调整并验证：

1. 将 CAM++/emotion2vec 实例数提高到至少 8，或保持每模型 4 个并重新设计调度。
2. 将 `local_gpu_concurrency` 从 4 提高到 8。
3. 在 GPU 0 上重新压测并监控显存、GPU 利用率和模型池 `waiting`。

只增加 CAM++/emotion2vec 实例数而保持 `local_gpu_concurrency=4`，预计不会带来对应收益。

测试结束后已关闭 8084，Qwen-ASR 的 8806 端口仍在监听。
