# 六实例194.81秒的阻塞点与优化顺序（2026-11-23）

结论：有优化空间。整轮由a3（194.531秒）和a4（189.750秒）决定，主要耗时是约160秒的分段处理流水线；其中最大已计时项是Qwen forward及token读回。另有已经确认的共享主事件循环阻塞：同步ITN/文本后处理会暂停其它请求的结果消费和新段补位。优先验证把该后处理迁出事件循环，再验证裁剪/发送隔离和prefill调度；KV整理是有明确计时成本的下一项。当前只读分析未实施优化、未重跑，不能承诺能降到某个具体秒数。

## 最慢请求a3的端到端互斥阶段

|步骤|耗时|含义|
|---|---:|---|
|上传/整音频准备及HTTP收尾差额|约3.33秒|包含未分项的写临时文件、tensor加载等，不能全部叫网络|
|完整音频VAD|24.786秒|整文件VAD返回后才开始供给Qwen|
|分段处理流水线|161.750秒|窗口等待、裁剪、IPC、Qwen及段级汇合等重叠流水的墙钟|
|ITN/文本后处理|4.642秒|同步规范化、标点、语速/语种比例等|
|其它内部差额|约0.021秒|由整体计时减上列阶段|
|单条HTTP总耗时|194.531秒|整轮共同起点墙钟194.809秒，存在正常任务起跑偏移|

a4的相应VAD/分段/ITN为23.306/159.969/3.227秒。VAD约22～25秒，采样中八CPU池最多busy6、waiting0，没有持续VAD排队证据。音频准入和PCM预算waiting也未观察到持续积压；不应先靠增加VAD实例或PCM预算解释这轮长尾。

`gpu_time_ms`实际包含VAD、分段流水和ITN，不是纯NPU时间。`load_audio_time_ms`只含read与preprocess，不包含之后的tensor加载。最终requestTelemetry含六暖身和五条正式，a3最后原始事件未保存；本分析用按task_id匹配的六条正式耗时日志补齐a3阶段（取整毫秒），不拿混合P50冒充正式六音频。

## 1. 已确认的跨音频阻塞：ITN同步占用唯一事件循环

`api/routes/asr_qwen_common.py:883–907`在async主链路内直接调用normalize_segments、sanitize、语速/语言比例等，中间没有await。本服务只有一个uvicorn worker。它运行时，模型子进程仍可处理已提交段，但父服务无法及时消费结果、释放credit并补充新段。

本轮观察：

- a1规范化约3.713秒期间，a6模型末段已resource_reusable；主服务直到约3.207秒后才记录a6全部完成。
- a6整块ITN/文本后处理6.942秒，其中规范化约6.911秒；期间其他owner无新prefill，状态请求ReadTimeout，相邻状态记录出现6.408秒间隙。
- a4规范化约3.179秒期间，a3模型末段已完成；主服务完成进度延迟约0.638秒。

这些时序支持主loop阻塞及补位延迟。ITN区间起点由日志end减包络近似回推，未装作精确事件trace。不能把六个ITN累计时间全部当成可直接省下的整轮时间；它们与其它模型工作存在交叠。

优先候选：把完整文本后处理放到独立、有界、初始仅一个worker的专用执行器，主loop只发布结果及阶段统计。不能直接复用已与Pipe争用的默认pool，也不能未经验证就开多线程调用共享normalizer：现有_CACHE_LOCK仅保护实例构造，normalize调用没有调用锁。取消仍等待实际工作结束，线程/进程统一归属关闭。若GIL仍影响loop，再用实测决定是否需要进程。

验收看loop lag、ITN窗口内其它音频prefill推进、completion→补位、状态延迟、a3/a4与整轮墙钟；文本、标点、语速/语言字段及错误行为必须与原策略一致。

## 2. 最大执行包络：频繁小prefill和decode

扣六次暖身后，3752段触发2138次prefill，平均仅1.755段/次（配置上限16）；decode4297步。每个owner先执行一个prefill再推进decode，大量小批反复发生输入准备、forward发起和读回。同一owner的旧序列会在该prefill期间等待下一步decode，这里没有旧HF generate整批返回的屏障。

a3自身已计时prefill/decode73.139/72.258秒，其中forward+readback合121.953秒；a4为69.809/80.977秒，其中forward+readback128.118秒。前者包括device排队、kernel、启动和同步读回，不能等同纯NPU算力，也不能据此认定硬件已饱和。

优先先改善已ready成员的供给，再独立比较prefill/decode交替策略，保持逐段EOS、每音频16/global96及有限补位延迟。只把prefill上限16调大不会自动把实际1.755变大；不能通过久等凑满重新引入整批屏障，也不能让新prefill饿死旧decode。

供给路径有具体问题：裁剪/编码和持锁阻塞Pipe提交共用asyncio.to_thread默认pool，sender pending采样峰31；a3提交锁/写入累计24.191/37.628秒、a4为21.009/34.120秒。但这些是并发段累计，已含于调用驻留，不能加到wall，也不能据一个峰值认定全程满池。裁剪内部函数工作遥测最大约4.289秒，dispatch/回调累计等待最大108.222秒（仍是含暖身及五正式的已保存子集），说明长“裁剪耗时”主要不能当纯裁剪CPU计算；精确线程池争用份额还未知。

独立有界裁剪pool和每owner专用有界FIFO sender可作为单因素候选。此前S1仅有独立候选契约/短准入，不是当前六实例真实性能已验证；当前194.81秒未包含S1优化。

## 3. KV布局与每步统计有进一步空间

|a3内部已计时项|耗时|边界|
|---|---:|---|
|forward+readback|121.953秒|含NPU执行/等待/读回，非纯kernel|
|KV布局|11.322秒|select/pad/cat/permutation等，已含于decode|
|processor输入前端|5.920秒|已含于prefill|
|序列bookkeeping|4.581秒|已含于对应模型步|

这些子项包含在a3已计时运行约145.691秒内，不与prefill/decode总数再相加。与分段流水161.750秒之间约16.059秒尚未完全拆清，含供给/回调、步间receive/poll、每步诊断扫描等，不能全部视为可消除浪费。a4已计时151.213秒，未覆盖包络约8.756秒；只优化a3时a4很快会成为整轮末请求，需共同改善公共路径。

代码确认的候选：先裁掉历史无效padding再select；省略identity选择/不必要permutation与copy；减少成员变化时全层重打包。本轮3151次KV重排、1146次直接布局沿用，这不是跨VAD语义缓存命中率。HF DynamicLayer.update内部每token仍用cat扩展K/V，外部布局直接沿用也非零复制。

此外_refresh_memory在每次prefill/decode之后扫描活跃成员/层/storage，本轮至少6435次调用，处于现有phase计时之外。它的成本尚未单独计时；先补计时，再决定按group增量记账或降低物理storage统计频率，不能把未覆盖16秒全部归给它，也不能牺牲缓存所有权/资源峰值口径。

## 后续验证顺序

1. 最先做ITN专用执行器的单因素真实A/B，确认事件循环及其它音频补位恢复；不同时更改模型生成和KV布局。
2. 再验证专用裁剪/发送供给与现成ready的prefill调度，区分哪部分改善实际微批密度/关键请求。
3. 按独立计时验证KV复制与统计扫描，较大的固定槽位/缓存布局改造需要额外正确性证据。

各候选继续使用同六条完整WAV、六实例、真实v3、16/96、用户已关闭HBM提前停止的策略以及336秒截止，复核输出/段警告与全部资源闭环。当前仍有16段警告、13段丢弃及32处a5配对文本变化，不能用少输出换速度，不能从单轮候选推定八音频或稳定性已通过。
