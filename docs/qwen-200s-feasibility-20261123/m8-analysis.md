整卡driver used/free=58202/7334MiB，可用于资源闸门。driver进程表只观测7个owned：warmup部分和32557MiB、diag部分和36395MiB；两次均缺owner7 PID3256974，八owned完整driver合计必须为unknown/null。allocator八份都在，不可拿7份driver和对齐8份allocator。

只读parser显示无显式8行/进程限额：遍历所有stdout行、符合格式即append；缺PID已经不在parsed compute_apps里，而非ownership过滤丢弃。卡7恰8行=原服务1+owned7，与CLI表可见条数限制相容，但本轮未保留raw stdout，不能确认driver/CLI/格式的具体原因。

## 对静态路径的实测校准

小prefill确实存在（平均2.403），KV布局包络跨8owner累计2.251秒、bookkeeping1.939秒；这些值有重叠并含设备等待，不是纯kernel，也不能把reserved增长全归于KV。默认线程池/Pipe锁路径仍在，但本轮末端pending仅1，不支持把大规模发送排队当已证主要卡点。每步_refresh_memory扫描尚未单独计时，仍是待证线索。14400帧导致最长16段拆15+1的路径是代码事实，当前小批平均值本身不能证明预算是主因。

没有任何正式音频完成，requestTelemetry completed=8及phase分位数全来自暖身；正式裁剪dispatch等待分布未知。pipeline在诊断时active128、budget waiting0，只说明该瞬间非PCM预算反压，不能证明没有裁剪线程排队。

收尾文件已存在=True。normalexit=0、forced=False、TERM至退出58.729秒、passed=True。
